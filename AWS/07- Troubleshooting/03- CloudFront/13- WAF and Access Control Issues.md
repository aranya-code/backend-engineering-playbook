# 13- WAF and Access Control Issues

## Overview

AWS WAF and CloudFront access-control failures are a common source of unexpected `403 Forbidden` responses. The difficulty is that several independent security layers can reject the same request:

```text
Client
   │
   ▼
CloudFront
   │
   ├── AWS WAF
   ├── CloudFront behavior
   ├── Signed URL / Signed Cookie
   ├── Origin access controls
   │
   ▼
Origin
   │
   ├── ALB / Nginx
   ├── Application
   └── Authorization
```

A `403` therefore does not automatically mean that the application denied the request.

The primary troubleshooting objective is to determine **which layer rejected the request**.

Typical causes include:

- AWS WAF rule blocks
- WAF managed rule false positives
- IP or geographic restrictions
- Rate-based WAF rules
- CloudFront signed URL or signed cookie failures
- CloudFront origin access configuration
- S3 bucket policy or Origin Access Control configuration
- CloudFront behavior mismatches
- Origin application authorization
- Security controls implemented at Nginx, ALB, Django, or FastAPI

The most important operational principle is:

> **Trace the request through every enforcement layer instead of debugging the origin first.**

## Request Enforcement Flow

A simplified request path is:

```mermaid
flowchart TD
    A[Client Request] --> B[DNS]
    B --> C[CloudFront Edge]
    C --> D{AWS WAF Attached?}

    D -->|Yes| E[Evaluate WAF Rules]
    E -->|Blocked| F[403 Response]
    E -->|Allowed| G[CloudFront Behavior]

    D -->|No| G

    G --> H{Viewer Access Control}
    H -->|Denied| F
    H -->|Allowed| I{Origin Access Control}

    I --> J[Origin]
    J --> K{Application Authorization}
    K -->|Denied| F
    K -->|Allowed| L[Response]
```

This flow is conceptual rather than a literal guarantee of every internal processing step. The exact enforcement behavior depends on the configured CloudFront distribution, WAF rules, cache behavior, and origin.

## Distinguishing WAF 403 From Other 403 Responses

A `403 Forbidden` response can originate from multiple components.

| Potential source | Typical cause |
|---|---|
| AWS WAF | Rule matched and blocked request |
| CloudFront signed URL | Missing, invalid, or expired signature |
| CloudFront signed cookie | Missing or invalid policy/signature |
| CloudFront | Distribution or behavior-level restriction |
| S3 | Bucket policy or object access denied |
| Origin Load Balancer | Listener or security policy |
| Nginx | IP, host, path, or authentication rule |
| Django | Application authorization |
| FastAPI | Application authorization/dependency |
| Custom origin | Server-side access policy |

Do not use the HTTP status code alone to identify the source.

## AWS WAF Integration With CloudFront

AWS WAF can be associated with a CloudFront distribution to inspect incoming HTTP requests.

Conceptually:

```text
Client
   │
   │ HTTPS
   ▼
CloudFront
   │
   ▼
AWS WAF
   │
   ├── Allow
   ├── Block
   ├── Count
   └── Challenge / CAPTCHA
   │
   ▼
CloudFront
   │
   ▼
Origin
```

WAF evaluates request attributes such as:

- URI path
- HTTP method
- Headers
- Cookies
- Query parameters
- Source IP
- Geographic origin
- Request rate
- Labels generated by other rules
- Managed rule matches

A blocked request may never reach the origin.

## Why WAF Blocks Are Difficult to Diagnose

Suppose:

```text
GET /api/orders
```

returns:

```http
HTTP/2 403
```

and the Django application logs contain nothing.

This can be expected if WAF rejected the request before CloudFront forwarded it.

The investigation should therefore move upstream:

```text
Django logs
     ↓
CloudFront logs
     ↓
WAF logs
     ↓
WAF rules
```

Rather than assuming that the application is broken.

## Check Whether WAF Is Associated

Inspect the CloudFront distribution:

```bash
aws cloudfront get-distribution \
  --id "$DISTRIBUTION_ID" \
  --query 'Distribution.DistributionConfig.WebACLId'
```

If a Web ACL ARN is configured, inspect that Web ACL.

For example:

```bash
aws wafv2 get-web-acl \
  --name "$WEB_ACL_NAME" \
  --scope CLOUDFRONT \
  --id "$WEB_ACL_ID" \
  --region us-east-1
```

CloudFront-scoped AWS WAF resources use the `CLOUDFRONT` scope and are managed in `us-east-1`.

## WAF Rule Evaluation

A Web ACL contains rules that evaluate requests.

A simplified example:

```text
Request
   │
   ▼
Rule A: Allow trusted IPs
   │
   ▼
Rule B: Block malicious patterns
   │
   ▼
Rule C: Managed rules
   │
   ▼
Rule D: Rate limiting
   │
   ▼
Default action
```

Rule priority matters.

A request can match multiple rules, but the resulting behavior depends on rule actions and evaluation order.

## WAF Actions

Common actions include:

| Action | Behavior |
|---|---|
| Allow | Permit request to continue |
| Block | Reject request |
| Count | Record match without blocking |
| CAPTCHA | Require CAPTCHA validation |
| Challenge | Require browser challenge |
| Override | Modify behavior of selected managed-rule matches |

For troubleshooting, `Count` is particularly useful when validating whether a suspected rule is responsible for production traffic.

## Count Before Block

When a WAF rule appears to be causing false positives, changing it directly from:

```text
Block
```

to:

```text
Allow
```

can be dangerous.

A safer troubleshooting workflow is:

```text
Block
  ↓
Count
  ↓
Observe real traffic
  ↓
Inspect sampled/logged requests
  ↓
Tune rule
  ↓
Restore Block
```

This allows engineers to validate the rule without immediately creating a security bypass.

## WAF Logging

WAF logs provide much more useful information than a generic `403`.

Enable WAF logging through an appropriate AWS logging destination and inspect:

- Timestamp
- Action
- Rule ID
- Rule group
- Client IP
- URI
- HTTP method
- Headers
- Labels
- Request metadata

The key question is:

> **Which rule produced the terminating decision?**

## Investigating WAF Logs

A typical WAF log investigation should identify:

```text
Request
   │
   ├── Source IP
   ├── URI
   ├── Method
   ├── Headers
   └── Query parameters
          │
          ▼
     Rule evaluation
          │
          ▼
   Terminating rule
          │
          ▼
      Block/Allow
```

When investigating a single request, correlate timestamps carefully because distributed systems can produce events across multiple services.

## Managed Rule False Positives

AWS Managed Rules are designed to detect common attack patterns, but legitimate application traffic can occasionally match a security rule.

Examples include:

- JSON payloads resembling SQL injection
- Search parameters containing suspicious strings
- Rich text fields containing scripting-like content
- API parameters resembling command injection
- Framework-generated request formats
- Encoded values

A common mistake is disabling the entire managed rule group.

Prefer targeted exceptions.

For example:

```text
Managed rule group
       │
       ├── Rule A → keep enabled
       ├── Rule B → keep enabled
       ├── Rule C → targeted scope-down/exclusion
       └── Rule D → keep enabled
```

## Scope-Down Statements

Scope-down logic can limit where a rule applies.

For example, a managed rule may be unnecessary for a trusted application endpoint with a known request shape.

Conceptually:

```text
All requests
     │
     ▼
Scope-down condition
     │
     ├── Matching traffic → evaluate managed rule
     └── Other traffic → bypass that rule
```

Use scope-down conditions carefully. The objective is to reduce false positives without creating a broad security gap.

## WAF Rate-Based Rules

Rate-based rules can block clients that exceed a configured request rate.

A legitimate API consumer may unexpectedly trigger a rate limit because of:

- Client retries
- Polling
- Broken frontend code
- Mobile network retries
- NAT gateways
- Corporate proxies
- Load testing
- Bot traffic

A critical issue with IP-based rate limiting is that many legitimate users can share one public IP.

For example:

```text
Corporate Network
       │
       ├── User A
       ├── User B
       ├── User C
       ├── User D
       └── User E
             │
             ▼
       One public IP
             │
             ▼
         WAF rule
```

The rate limit applies to the identity used by the rule, which may cause unrelated users to be affected.

## Rate-Based Rule Troubleshooting

Check:

- Request rate
- Source IP
- NAT behavior
- API clients
- Retry behavior
- Endpoint popularity
- Legitimate traffic spikes
- Load tests
- Automated jobs

Do not simply increase the limit until the errors disappear.

First determine why traffic is exceeding the threshold.

## Geographic Restrictions

Access restrictions can exist at both CloudFront and WAF layers.

For example:

```text
CloudFront geographic restriction
        +
AWS WAF geographic rule
        +
Application authorization
```

A request can therefore be denied based on geographic policy before reaching the application.

When troubleshooting regional access failures, determine whether the restriction is:

- CloudFront geographic restriction
- WAF geo match rule
- Origin firewall
- Application logic

## CloudFront Geographic Restrictions

CloudFront can restrict access based on viewer location.

Check distribution configuration:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID" \
  --query 'DistributionConfig.Restrictions'
```

A production incident affecting only certain countries should immediately make geographic controls part of the investigation.

## IP Allowlisting

IP-based access controls are common for:

- Internal APIs
- Administrative interfaces
- Partner integrations
- CI/CD systems
- Monitoring endpoints

But CloudFront receives requests from users distributed across the Internet, and the relevant client IP must be understood correctly.

Do not build an allowlist around the assumption that all requests originate from your office or VPN IP if the actual architecture includes proxies, NAT, or distributed workers.

## Client IP and Forwarded Headers

Applications may inspect headers such as:

```text
X-Forwarded-For
```

However, security-sensitive authorization decisions should not blindly trust client-supplied forwarding headers.

A request can contain arbitrary headers unless a trusted intermediary establishes and controls them.

The architecture must define:

```text
Trusted proxy
     │
     ▼
Client IP extraction
     │
     ▼
Authorization
```

Do not let an attacker spoof an IP allowlist by manually setting a header.

## Signed URL and Signed Cookie Interaction

CloudFront signed URLs and signed cookies provide a separate access-control mechanism from WAF.

A request might therefore pass WAF but still fail authorization:

```text
Client
   │
   ▼
WAF → Allow
   │
   ▼
CloudFront
   │
   ▼
Signed URL validation → Fail
   │
   ▼
403
```

When protected content returns `403`, inspect both:

- WAF decision
- CloudFront signed-request validation

## Signed URL Troubleshooting

Common causes include:

- Missing signature parameters
- Expired URL
- Incorrect expiration
- Invalid key pair
- Wrong key group configuration
- Signature generated incorrectly
- URL modified after signing
- Resource path mismatch
- Policy mismatch
- Clock-related assumptions

A signed URL should be treated as an immutable security artifact.

If an application modifies the URL after signing, validation can fail.

## Signed Cookie Troubleshooting

Signed cookies are useful when a client needs access to multiple objects without generating a separate signed URL for each object.

Typical problems include:

- Missing cookie
- Wrong cookie names
- Expired policy
- Incorrect signature
- Invalid key group
- Incorrect policy
- Cookie domain/path mismatch
- Browser cookie restrictions

Inspect the browser request and verify that the expected CloudFront signing cookies are actually being sent.

## Browser Cookie Domain Problems

Suppose the content is served from:

```text
cdn.example.com
```

but the cookie is scoped incorrectly.

The browser may not send the cookie to the CloudFront hostname.

This produces a server-side symptom that looks like:

```text
Valid cookie generated
       ↓
Browser stores incorrectly
       ↓
Cookie not sent
       ↓
CloudFront sees no authorization
       ↓
403
```

Always inspect the actual network request rather than assuming the browser stored the cookie correctly.

## Origin Access Control

When CloudFront accesses an S3 origin, Origin Access Control (OAC) can be used to authorize CloudFront-origin requests.

A common architecture is:

```text
Client
  │
  ▼
CloudFront
  │
  │ Signed AWS request
  ▼
S3
```

If S3 rejects the CloudFront request, the client may receive an error that appears to be a CloudFront access problem.

## S3 403 Through CloudFront

Potential causes include:

- Incorrect S3 bucket policy
- Incorrect OAC configuration
- Distribution pointing to the wrong bucket
- Object does not exist
- Missing object permissions
- Incorrect resource ARN
- Incorrect account
- Incorrect region or endpoint configuration
- Encryption/KMS authorization problems

The distinction between a missing object and an authorization failure can be subtle because S3 may intentionally avoid exposing object existence details.

## Inspect Origin Configuration

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID" |
jq '.DistributionConfig.Origins.Items[]'
```

Check:

- Origin ID
- Domain name
- Origin access configuration
- Custom headers
- Protocol settings

For an S3 origin, verify that the configured bucket and CloudFront access model match the bucket policy.

## S3 Bucket Policy

A bucket policy should grant the required access to the intended CloudFront distribution rather than broadly exposing the bucket.

Avoid patterns such as:

```json
{
  "Principal": "*",
  "Action": "s3:GetObject"
}
```

for private content merely to make CloudFront requests succeed.

Security should be fixed at the policy boundary rather than bypassed.

## KMS-Encrypted S3 Objects

If objects use SSE-KMS, the CloudFront access path may require appropriate KMS permissions.

The troubleshooting chain becomes:

```text
CloudFront
   │
   ▼
S3 authorization
   │
   ▼
KMS authorization
   │
   ▼
Object access
```

A bucket policy can appear correct while the KMS key policy still prevents the required operation.

## CloudFront Cache Behavior Problems

A request can be routed to the wrong cache behavior.

For example:

```text
/api/*
    → API origin

/images/*
    → S3 origin
```

If behavior ordering or path patterns are incorrect, a request may reach an unexpected origin and receive a `403`.

Inspect behaviors:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID" |
jq '.DistributionConfig.CacheBehaviors'
```

Also inspect the default cache behavior.

## Path Pattern Mistakes

Consider:

```text
/images/*
```

versus:

```text
/image/*
```

A request to:

```text
/images/logo.png
```

may therefore fall through to the default behavior.

That default behavior may point to an origin that does not contain the requested object.

This can produce an apparently unrelated `403` or `404`.

## Query Strings and Authorization

Security decisions can depend on query parameters.

For signed URLs, the signature-related parameters are part of the authorization mechanism.

For WAF rules, query parameters may also be inspected.

Do not casually normalize or remove query parameters at Nginx, application, or proxy layers without understanding their security role.

## HTTP Method Restrictions

CloudFront cache behaviors can restrict which HTTP methods are allowed.

For example:

```text
GET
HEAD
OPTIONS
```

may be allowed while:

```text
POST
PUT
PATCH
DELETE
```

are not forwarded.

For APIs, verify that the CloudFront behavior is configured for the required methods.

A method mismatch can appear as an access-control failure even though WAF is not responsible.

## Origin Application Authorization

Not every `403` is infrastructure-level.

A Django application may return:

```python
from django.http import JsonResponse


def protected_view(request):
    if not request.user.is_authenticated:
        return JsonResponse({"detail": "Forbidden"}, status=403)

    return JsonResponse({"status": "ok"})
```

A FastAPI service may similarly reject a request through an authorization dependency.

If the request reaches the origin, inspect:

- Application logs
- Authentication middleware
- Authorization policies
- JWT validation
- API keys
- RBAC
- Tenant permissions
- CSRF protection
- Host validation

## Nginx Access Controls

Nginx may also return `403`.

Potential causes include:

```nginx
allow 10.0.0.0/8;
deny all;
```

or filesystem permissions, location restrictions, and authentication configuration.

When CloudFront sits in front of Nginx:

```text
Client
  ↓
CloudFront
  ↓
Nginx
  ↓
Django/FastAPI
```

a `403` can originate from any layer.

## Diagnostic Layering

Use a strict investigation order:

```text
DNS
 ↓
CloudFront
 ↓
WAF
 ↓
CloudFront access controls
 ↓
Origin access controls
 ↓
ALB/Nginx
 ↓
Application
```

The exact order can vary depending on the architecture, but the principle is to identify the rejecting layer before changing configuration.

## Logging Strategy

A production CloudFront security investigation should correlate:

- CloudFront request ID
- Timestamp
- Client IP
- Host
- URI
- HTTP method
- WAF action
- WAF rule
- Origin status
- HTTP status
- User/session identity where available

Useful observability sources include:

- AWS WAF logs
- CloudFront logs
- CloudFront metrics
- Application logs
- Nginx logs
- ALB access logs
- S3 access logs or CloudTrail where applicable
- AWS CloudTrail configuration events

## CloudFront and WAF Metrics

Monitor trends rather than only individual errors.

Useful signals include:

| Signal | Meaning |
|---|---|
| Allowed requests | Normal traffic |
| Blocked requests | Security enforcement |
| WAF rule matches | Potential attacks or false positives |
| CloudFront 4xx | Viewer/access problems |
| CloudFront 5xx | Origin/service problems |
| Origin request count | Traffic reaching origin |
| Origin latency | Backend performance |
| Error-rate change after WAF deployment | Potential false positive |

A sudden increase in blocked requests after a WAF rule deployment is a strong correlation signal.

## Correlating Configuration Changes

For an unexpected access-control incident, inspect recent changes:

```text
WAF rule change
      │
      ├── Managed rule update
      ├── Rule priority change
      ├── Rate-limit change
      └── IP/geo rule change

CloudFront change
      │
      ├── Behavior
      ├── Origin
      ├── Signed access
      └── Distribution configuration

Application change
      │
      ├── Authentication
      ├── Authorization
      └── Middleware
```

Many security incidents are configuration regressions rather than application bugs.

## Production Troubleshooting Procedure

### Identify the Exact Request

Capture:

```text
Hostname
URI
HTTP method
Timestamp
Client IP
Query parameters
Cookies
Relevant headers
```

Do not investigate only from a generic browser error page.

### Reproduce With `curl`

```bash
curl -v \
  --connect-timeout 10 \
  --max-time 30 \
  "https://cdn.example.com/protected/resource"
```

If signed access is involved, reproduce with the exact signed request.

### Determine Whether WAF Blocked It

Inspect WAF logs and identify:

```text
Action
Rule ID
Rule group
Source IP
URI
```

If WAF blocked the request, the origin is usually not the first place to investigate.

### Check CloudFront Access Controls

Inspect:

- Signed URL requirements
- Signed cookie requirements
- Allowed HTTP methods
- Geographic restrictions
- Cache behavior
- Origin configuration

### Check Origin Access

For S3:

```text
CloudFront → OAC → S3
```

For a custom origin:

```text
CloudFront → HTTPS → ALB/Nginx/application
```

Verify the origin authorization model.

### Check Application Logs

Only after establishing that the request reached the origin should you spend significant time debugging:

- Django
- FastAPI
- Nginx
- ALB
- Kubernetes ingress
- Backend authorization

## Safe WAF Rule Tuning

A production WAF rule should be tuned using evidence.

Recommended process:

```text
Identify blocked request
        ↓
Find terminating rule
        ↓
Understand why it matched
        ↓
Determine legitimate or malicious
        ↓
If legitimate, design narrow exception
        ↓
Count / observe
        ↓
Validate
        ↓
Restore blocking behavior
```

Avoid broad allow rules such as:

```text
Allow all requests from a large IP range
```

unless the trust boundary genuinely justifies it.

## Security Considerations

Access-control troubleshooting must not result in permanent security weakening.

Avoid:

- Disabling WAF globally
- Allowing all IPs
- Making private S3 buckets public
- Removing signed URL requirements
- Removing signed cookie requirements
- Bypassing authentication
- Trusting arbitrary `X-Forwarded-For` values
- Disabling origin authentication
- Creating broad WAF allow rules
- Exposing administrative endpoints

A temporary mitigation should have:

```text
Owner
Reason
Scope
Expiration
Rollback
Monitoring
```

## Scalability Considerations

WAF is designed to operate at the CloudFront edge, allowing unwanted traffic to be rejected before it consumes origin capacity.

This is particularly important for:

- Public APIs
- High-traffic websites
- Login endpoints
- Search endpoints
- Expensive backend operations

For example:

```text
10 million requests
      │
      ▼
CloudFront
      │
      ├── 8 million blocked/filtered
      │
      └── 2 million allowed
              │
              ▼
            Origin
```

The exact numbers are illustrative, but the architectural principle is important:

> **Reject unwanted traffic as close to the client as practical.**

## Origin Protection

WAF should complement, not replace, origin protection.

A production architecture should consider:

```text
Internet
   │
   ▼
CloudFront
   │
   ├── WAF
   ├── Rate limiting
   └── Access control
   │
   ▼
Origin
   │
   ├── Network controls
   ├── Authentication
   ├── Authorization
   └── Application validation
```

Defense in depth prevents a single misconfiguration from exposing the backend.

## Common Production Pitfalls

| Pitfall | Why it happens | Better approach |
|---|---|---|
| Disable WAF to fix 403s | Fast but unsafe | Identify terminating rule |
| Allow entire IP range | Easy workaround | Use narrow exceptions |
| Ignore signed access | Assume WAF is responsible | Validate CloudFront authorization |
| Debug application first | Familiarity with backend | Prove request reached origin |
| Make S3 public | Simplifies access | Correct OAC/bucket policy |
| Trust forwarded IP headers | Misunderstanding proxy chain | Define trusted proxy boundaries |
| Ignore cache behaviors | Wrong origin receives request | Inspect path pattern ordering |
| Remove query parameters | Proxy normalization | Preserve security-relevant parameters |
| Increase WAF rate limit blindly | Stops symptoms | Investigate traffic source |
| Modify production WAF directly | Emergency pressure | Use controlled, auditable changes |

## Interview Perspective

A strong answer to:

> "CloudFront is returning 403. How would you determine whether WAF is responsible?"

should be structured around the enforcement layers:

1. Reproduce the exact request.
2. Capture timestamp, hostname, URI, method, and source information.
3. Check whether the CloudFront distribution has an associated WAF Web ACL.
4. Inspect WAF logs for the request.
5. Identify the terminating rule and action.
6. Determine whether the match is legitimate or a false positive.
7. If WAF allowed the request, inspect CloudFront signed URL/cookie requirements.
8. Check CloudFront behaviors, geographic restrictions, and method restrictions.
9. If the request reached the origin, inspect origin authorization.
10. For S3, verify OAC and bucket/KMS permissions.
11. For ALB/Nginx/Django/FastAPI, inspect their access-control logs.
12. Correlate the incident with recent WAF, CloudFront, DNS, and application changes.

The senior-level distinction is:

> **A CloudFront 403 is an access-control symptom, not a root cause. The root cause is the first security or authorization layer that rejects the request.**

## Key Takeaways

- **A CloudFront 403 can originate from multiple layers:** identify whether WAF, CloudFront, origin access controls, Nginx, or the application rejected the request.
- **Use WAF logs to identify the terminating rule:** do not disable the Web ACL or broad-allow traffic simply to eliminate the symptom.
- **Treat signed URLs, signed cookies, OAC, S3 policies, and application authorization as separate security boundaries.**
- **Troubleshoot from the edge toward the origin:** prove that a request passed each enforcement layer before debugging the next one.
- **Prefer narrow, observable security changes:** use counting, targeted exceptions, logging, monitoring, and controlled rollback rather than broad security bypasses.
