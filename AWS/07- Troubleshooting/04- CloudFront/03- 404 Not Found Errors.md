# 03- 404 Not Found Errors

## Overview

A `404 Not Found` response through Amazon CloudFront means the requested resource could not be resolved at some point in the request path. The important troubleshooting distinction is that the `404` may be generated by CloudFront itself, by the origin, or by an application behind the origin.

Typical request paths include:

```text
Client
  │
  ▼
CloudFront
  │
  ├── Cache lookup
  ├── Cache behavior
  ├── Viewer request processing
  │
  ▼
Origin
  │
  ├── S3
  ├── ALB
  ├── Nginx
  └── Django / FastAPI
```

A production investigation should therefore answer four questions:

1. Does the requested resource actually exist?
2. Did CloudFront route the request to the expected origin?
3. Did the origin receive the expected path?
4. Which component generated the `404`?

The most common causes are incorrect paths, missing S3 objects, incorrect origin paths, cache behavior mismatches, application routing errors, deployment inconsistencies, and stale cached responses.

## What a CloudFront 404 Represents

A `404` indicates that the requested resource could not be found. It does **not** necessarily mean that CloudFront itself could not find the resource.

For example:

```text
Client
  │
  │ GET /assets/app.js
  ▼
CloudFront
  │
  │ cache miss
  ▼
S3
  │
  │ object does not exist
  ▼
404
  │
  ▼
CloudFront
  │
  ▼
Client
```

The client sees:

```http
HTTP/2 404 Not Found
```

but the actual problem is the missing S3 object.

Conversely, CloudFront configuration itself can result in a request being handled differently from what the engineer expects.

## Identify the Source of the 404

The first troubleshooting task is to identify where the response originated.

| Layer | Example cause |
|---|---|
| CloudFront | Edge-generated error or request processing issue |
| Cache | Previously cached error response |
| Cache behavior | Request routed to unexpected origin |
| S3 | Object does not exist |
| ALB | Backend route does not exist |
| Nginx | Incorrect location or rewrite |
| Django | URL route does not exist |
| FastAPI | Endpoint does not exist |
| Application | Dynamic resource does not exist |

A `404` should therefore be treated as a **request-path debugging problem**, not simply a missing-file problem.

## Reproduce the Exact Request

Start with the exact failing URL:

```bash
curl -sv https://cdn.example.com/assets/app.js
```

Inspect only response headers:

```bash
curl -sS -D - -o /dev/null \
  https://cdn.example.com/assets/app.js
```

Record:

- HTTP method
- Full URL
- Path
- Query string
- Hostname
- Response status
- Response headers
- Response body
- Timestamp
- Client environment
- Whether the resource previously worked

For browser requests, also inspect:

- Browser Network tab
- Redirect chain
- Request URL
- Response headers
- Cache status
- Query parameters
- Referer
- Cookies where relevant

## Compare CloudFront and Origin

When the origin is directly accessible, compare the two paths.

CloudFront:

```bash
curl -sv \
  https://cdn.example.com/assets/app.js
```

Origin:

```bash
curl -sv \
  https://origin.example.com/assets/app.js
```

Interpret the result carefully.

| CloudFront | Origin | Likely direction |
|---|---|---|
| `404` | `404` | Origin/resource problem |
| `404` | `200` | CloudFront routing, path transformation, or cache issue |
| `200` | `404` | Different request paths or CloudFront cache may be involved |
| `404` | inaccessible | Continue with CloudFront and origin configuration |
| `404` only for one path | `200` elsewhere | Path-specific configuration or application routing |

Direct-origin testing is not always equivalent to CloudFront because CloudFront can use different headers, paths, behaviors, and authorization mechanisms.

## Inspect the Distribution

Retrieve the distribution configuration:

```bash
aws cloudfront get-distribution \
  --id "$DISTRIBUTION_ID"
```

Retrieve only the configuration:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID"
```

A useful inspection command is:

```bash
aws cloudfront get-distribution \
  --id "$DISTRIBUTION_ID" \
  --query 'Distribution.{Id:Id,Domain:DomainName,Status:Status,Enabled:DistributionConfig.Enabled}' \
  --output table
```

Check:

- Distribution status
- Enabled state
- Alternate domain names
- Origins
- Default cache behavior
- Ordered cache behaviors
- Origin paths
- Functions/Lambda@Edge
- Error responses
- Viewer protocol policy

## Check Cache Behaviors

CloudFront can route different URL patterns to different origins.

For example:

```text
/                  → S3 static site
/assets/*          → S3 assets
/api/*             → ALB
/media/*           → S3 media
```

Inspect cache behaviors:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID" \
  --query 'DistributionConfig.{Default:DefaultCacheBehavior,Behaviors:CacheBehaviors}'
```

The important question is:

> Which cache behavior handles the failing path?

For:

```text
/api/users
```

verify that the request is actually handled by:

```text
/api/*
```

rather than the default behavior.

An incorrect path pattern can route the request to an origin that does not contain the requested resource.

## Path Pattern Matching

Suppose the intended configuration is:

```text
/api/*       → API origin
/assets/*    → Static origin
```

If the `/api/*` behavior is missing, `/api/users` may fall through to the default behavior.

The resulting flow can be:

```text
/api/users
    │
    ▼
No matching /api/* behavior
    │
    ▼
Default behavior
    │
    ▼
Static S3 origin
    │
    ▼
Object not found
    │
    ▼
404
```

The application may be completely healthy.

The problem is the CloudFront routing configuration.

## Origin Path Problems

An origin can have an origin path configured.

For example:

```text
CloudFront viewer path:
/assets/app.js

Origin path:
/production

Origin request:
/production/assets/app.js
```

The effective request path is therefore not simply:

```text
/assets/app.js
```

When debugging a `404`, explicitly map:

```text
Viewer URL
    ↓
Cache behavior
    ↓
Target origin
    ↓
Origin path
    ↓
Effective origin request
```

A common mistake is creating a directory structure in S3 based on the CloudFront URL while forgetting that an origin path is already prepended.

## S3 Object Not Found

For S3-backed CloudFront distributions, verify the object directly.

```bash
aws s3api head-object \
  --bucket "$BUCKET_NAME" \
  --key "assets/app.js"
```

A successful response indicates that the object exists and can be inspected through the S3 API.

List a relevant prefix when necessary:

```bash
aws s3api list-objects-v2 \
  --bucket "$BUCKET_NAME" \
  --prefix "assets/"
```

For a deployment involving hashed assets:

```text
Expected:
assets/app.8f3a91.js

Actual:
assets/app.9c421e.js
```

CloudFront cannot compensate for a missing or incorrectly named object.

## S3 Key Names Are Exact

S3 object keys are case-sensitive.

These are different:

```text
assets/App.js
assets/app.js
```

Likewise:

```text
images/logo.png
images/logo.PNG
```

A browser request for:

```text
/assets/app.js
```

will not match:

```text
assets/App.js
```

This is a common source of production-only failures because local development environments may use case-insensitive filesystems.

## Static Website Hosting Versus S3 REST Origin

S3 can be integrated with CloudFront in different ways.

A private S3 bucket commonly uses the S3 REST endpoint with CloudFront Origin Access Control.

A static website endpoint behaves differently and can have different routing and error semantics.

When troubleshooting, verify the actual configured origin:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID" \
  --query 'DistributionConfig.Origins.Items[*].{Id:Id,DomainName:DomainName,OriginPath:OriginPath,OriginAccessControlId:OriginAccessControlId}'
```

Do not assume that an S3-backed CloudFront distribution is using the same request and error behavior as S3 static website hosting.

## Application-Level 404

If the CloudFront request reaches an application, the application may generate the `404`.

For Django:

```text
CloudFront
    ↓
ALB
    ↓
Nginx
    ↓
Django
    ↓
URL resolver
    ↓
404
```

For FastAPI:

```text
CloudFront
    ↓
ALB
    ↓
Nginx / Uvicorn
    ↓
FastAPI router
    ↓
404
```

Investigate:

- URL configuration
- Router registration
- HTTP method
- Path parameters
- API version
- Prefix configuration
- Reverse-proxy path rewriting
- Application deployment version

A CloudFront `404` does not mean the CDN is responsible for the missing route.

## Django Path Problems

Consider:

```python
urlpatterns = [
    path("api/users/", views.users),
]
```

A request to:

```text
/api/user/
```

will not match the route.

Likewise, reverse-proxy configuration can change the effective application path.

For example:

```text
Client:
/api/users

Nginx rewrite:
/users

Django route:
/users/
```

If these assumptions are inconsistent, the result can be a `404`.

## FastAPI Router Problems

FastAPI applications frequently use router prefixes:

```python
router = APIRouter(prefix="/api/users")
```

A deployment may therefore expose:

```text
/api/users
```

while the CloudFront behavior forwards:

```text
/users
```

Check:

- `APIRouter` prefixes
- Application root path
- Nginx rewrites
- ALB routing
- CloudFront path behavior
- API version prefixes

## Query Strings and Resource Identity

CloudFront cache behavior can make query strings important.

Consider:

```text
/image?id=123
/image?id=456
```

If the origin uses the query string to determine which resource to return, cache configuration must correctly account for that request variation.

Otherwise, CloudFront can return an object that does not correspond to the viewer's request.

For APIs, review:

- Cache policy
- Query-string forwarding
- Origin request policy
- Whether the endpoint should be cached at all

A common production design is to avoid caching personalized or authorization-sensitive API responses unless the cache key and forwarding configuration are deliberately designed.

## Cache-Cached 404 Responses

One of the most confusing scenarios is:

```text
Origin
  │
  └── Resource exists now → 200

CloudFront
  │
  └── Cached earlier 404 → 404
```

This can happen when an error response has been cached.

The important distinction is:

```text
Current origin state
        ≠
Current CloudFront cache state
```

When a resource was recently created, renamed, or deployed, determine whether CloudFront may still be serving an earlier error response.

## Check CloudFront Error Configuration

CloudFront supports custom error responses.

Inspect:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID" \
  --query 'DistributionConfig.CustomErrorResponses'
```

Review:

- Error code
- Error caching minimum TTL
- Response page path
- Response code

Custom error handling can make a `404` appear different from the underlying origin response.

For example:

```text
Origin:
404

CloudFront:
404 → /404.html
```

or a configured custom response may alter the status presented to the viewer.

## Cache Invalidation

If the resource was recently corrected or deployed, invalidate the affected path when appropriate.

```bash
aws cloudfront create-invalidation \
  --distribution-id "$DISTRIBUTION_ID" \
  --paths "/assets/app.js"
```

For a broader deployment:

```bash
aws cloudfront create-invalidation \
  --distribution-id "$DISTRIBUTION_ID" \
  --paths "/*"
```

Use broad invalidations carefully. A deployment strategy based on versioned or hashed assets is usually preferable to repeatedly invalidating the entire distribution.

## Check Invalidation Status

List recent invalidations:

```bash
aws cloudfront list-invalidations \
  --distribution-id "$DISTRIBUTION_ID"
```

Inspect a specific invalidation:

```bash
aws cloudfront get-invalidation \
  --distribution-id "$DISTRIBUTION_ID" \
  --id "$INVALIDATION_ID"
```

The operational sequence is:

```text
Deployment
    ↓
New object exists
    ↓
CloudFront may still have old response
    ↓
Invalidate targeted path if necessary
    ↓
CloudFront refreshes object
    ↓
Verify response
```

## Versioned Assets Are Preferable

For frontend or static asset deployments, prefer immutable asset names:

```text
app.a81c92.js
app.71f23a.js
```

rather than repeatedly overwriting:

```text
app.js
```

A deployment can then work like:

```text
Old:
app.a81c92.js

New:
app.71f23a.js
```

The new URL naturally causes a new cache lookup.

This reduces reliance on broad cache invalidations and improves cache consistency during deployments.

## Inspect Response Headers

Response headers can provide useful clues.

```bash
curl -sS -D - -o /dev/null \
  https://cdn.example.com/assets/app.js
```

Look for CloudFront-related headers and other indicators of how the response was generated.

A typical response may include information such as:

```text
HTTP/2 404
Via: ...
X-Cache: ...
```

The exact headers vary by configuration and AWS behavior, so treat them as evidence rather than as the sole source of truth.

## Check Origin Logs

If the origin is an ALB, inspect ALB access logs or relevant application logs.

For Nginx, investigate:

```text
access.log
error.log
```

For Django:

```text
application logs
```

For FastAPI:

```text
Uvicorn/application logs
```

The key question is:

> Did the origin receive this exact request?

If there is no corresponding origin request, focus on CloudFront behavior, cache, or edge processing.

If there is an origin request, inspect the exact path received.

## Compare Expected and Actual Paths

Create an explicit mapping during an incident:

| Layer | Expected | Actual |
|---|---|---|
| Viewer | `/assets/app.js` | `/assets/app.js` |
| Behavior | `/assets/*` | `/assets/*` |
| Origin path | `/production` | `/production` |
| Origin request | `/production/assets/app.js` | `/production/assets/app.js` |
| S3 key | `production/assets/app.js` | Missing |

This makes path mismatches visible much faster than inspecting configuration independently.

## CloudFront Functions and Lambda@Edge

Viewer-request or origin-request logic can modify requests.

Potential sources of `404` include:

- URI rewrites
- Redirect logic
- Path normalization
- Host-based routing
- Header-dependent routing
- Custom authentication logic

Inspect the distribution configuration for associated functions.

If a function changes:

```text
/assets/app.js
```

into:

```text
/static/app.js
```

the origin must contain the rewritten resource.

When debugging edge functions, compare:

```text
Original viewer URI
        ↓
Function transformation
        ↓
Effective origin URI
```

Do not troubleshoot only the original URL.

## Common 404 Patterns

| Symptom | Likely cause |
|---|---|
| All static files return `404` | Wrong origin or origin path |
| One static file returns `404` | Missing object or incorrect key |
| New deployment returns old `404` | Cached error |
| API route returns `404` | Application route or path rewrite |
| Only `/api/*` returns `404` | Cache behavior/origin routing |
| Only uppercase/lowercase variant fails | S3 key case mismatch |
| Direct S3 object works but CloudFront fails | Origin path, behavior, or CloudFront configuration |
| Direct origin works but CloudFront fails | Cache, path transformation, behavior, or edge logic |
| Some regions see `404` and others do not | Cache propagation, deployment state, or regional origin differences |
| `404` after frontend deployment | Asset manifest/version mismatch |

## Troubleshooting Workflow

### Capture the Failure

```bash
curl -sv https://cdn.example.com/assets/app.js
```

Record the exact request and timestamp.

### Verify the Resource

For S3:

```bash
aws s3api head-object \
  --bucket "$BUCKET_NAME" \
  --key "assets/app.js"
```

For an API:

```bash
curl -sv https://origin.example.com/api/users
```

### Identify the CloudFront Behavior

Inspect:

```bash
aws cloudfront get-distribution-config \
  --id "$DISTRIBUTION_ID"
```

Determine:

- Which behavior matches the path
- Which origin is selected
- Whether an origin path is configured
- Whether edge functions modify the URI

### Determine Whether the Origin Received the Request

Use:

- ALB access logs
- Nginx logs
- S3 evidence
- Application logs

### Compare Paths

Document:

```text
Viewer URI
→ Cache behavior
→ Origin path
→ Origin URI
→ Application route / S3 key
```

### Check Cache State

Determine whether CloudFront may be serving:

- Cached `404`
- Old object
- Old error response

Invalidate a targeted path if appropriate:

```bash
aws cloudfront create-invalidation \
  --distribution-id "$DISTRIBUTION_ID" \
  --paths "/assets/app.js"
```

### Verify the Fix

Test:

```bash
curl -fsS \
  https://cdn.example.com/assets/app.js \
  -o /dev/null
```

Then verify:

- Correct status
- Correct content
- Correct cache behavior
- Origin health
- No unintended routing changes

## Production Pitfalls

### Assuming the Object Exists

A deployment may report success while the expected asset was never uploaded.

Verify the actual object key rather than trusting the deployment process.

### Ignoring Case Sensitivity

Local development may work while production fails because S3 keys are case-sensitive.

Use exact paths consistently.

### Invalidating Everything

Using:

```text
/*
```

for every deployment is operationally simple but can be unnecessary and expensive at scale.

Prefer versioned assets and targeted invalidations.

### Debugging Only the Origin

An origin can return `200` while CloudFront still returns `404` because the edge is requesting a different path.

Always inspect the full request transformation.

### Debugging Only CloudFront

The inverse is also common.

If the origin application itself returns `404`, changing CloudFront configuration will not solve the underlying routing problem.

### Ignoring Custom Error Responses

A configured CloudFront error response can obscure the original origin behavior.

Inspect the distribution's custom error response configuration during troubleshooting.

### Deploying Application and CDN Changes Independently

A frontend can reference:

```text
app.newhash.js
```

before that file exists in the origin.

Use deployment ordering that guarantees referenced assets exist before clients receive the new HTML or API response.

## Deployment Strategy to Reduce 404s

A robust static-content deployment can follow:

```mermaid
flowchart TD
    A[Build application] --> B[Generate versioned assets]
    B --> C[Upload assets to S3]
    C --> D[Verify objects exist]
    D --> E[Deploy HTML / application references]
    E --> F[CloudFront serves new URLs]
    F --> G[Run smoke tests]
```

The important property is:

```text
Asset available before reference becomes public
```

For example:

```text
1. Upload app.abc123.js
2. Verify app.abc123.js
3. Deploy HTML referencing app.abc123.js
4. Verify through CloudFront
```

This is safer than:

```text
1. Deploy HTML
2. Upload app.abc123.js
```

because clients can request the new asset during the gap.

## Monitoring and Alerting

Monitor unexpected `404` rates rather than treating every `404` as an incident.

Useful dimensions include:

- URI/path
- Distribution
- Region
- Time
- Origin
- Deployment version
- User agent where appropriate

A sudden increase in `404` after a deployment is particularly valuable as an automated signal.

For example:

```text
Deployment
    │
    ▼
404 rate increases
    │
    ▼
Check asset availability
    │
    ├── Missing objects
    ├── Wrong paths
    ├── Cache behavior
    └── Application routes
```

Use CloudFront metrics together with origin and application telemetry. Aggregate metrics tell you that a problem exists; logs and request-level evidence usually tell you why.

## Interview Perspective

A strong answer to:

> "CloudFront is returning 404. What would you check?"

should demonstrate that you understand the entire request path.

A production-oriented investigation is:

1. Reproduce the exact URL.
2. Determine whether the `404` is cached or generated by the current request.
3. Check whether the resource exists at the origin.
4. Verify the matching CloudFront cache behavior.
5. Verify the target origin and origin path.
6. Compare the viewer URI with the effective origin URI.
7. Check S3 object keys or application routes.
8. Inspect CloudFront Functions or Lambda@Edge if request transformation is involved.
9. Check custom error responses.
10. Check origin logs to determine whether the request arrived.
11. Invalidate targeted cached responses when appropriate.
12. Verify the deployment sequence if the problem appeared after a release.

The important engineering principle is:

> **A 404 is a resource-resolution failure somewhere in the request path; do not assume the failing resource is missing until the path and generating layer have been verified.**

## Key Takeaways

- **A CloudFront `404` can originate at multiple layers:** identify whether the failure is in CloudFront, cache state, routing, S3, Nginx, or the application.
- **Trace the complete URI transformation:** verify the viewer path, cache behavior, origin path, effective origin URI, and final S3 key or application route.
- **Check deployment and cache state:** recently created resources can still appear missing because of stale cached error responses or deployment ordering problems.
- **Prefer immutable versioned assets:** hashed filenames reduce cache invalidation requirements and significantly reduce deployment-related `404` failures.
- **Use origin evidence:** determine whether the origin received the request before changing CloudFront configuration.
