# 04- AWS WAF and Request Filtering

## Overview

AWS WAF is a managed web application firewall that inspects HTTP(S) requests and applies rules before requests reach the protected application resource.

In a CloudFront architecture, AWS WAF provides the application-layer filtering capability that CloudFront itself does not provide as a general-purpose security policy engine.

A typical request path is:

```text
Client
  │
  │ HTTPS request
  ▼
CloudFront
  │
  ▼
AWS WAF
  │
  ├── Allow ───────────────► Origin
  │
  ├── Block
  │
  ├── Count
  │
  └── Challenge / CAPTCHA
```

This distinction is important:

| Component | Primary responsibility |
|---|---|
| CloudFront | Edge delivery, caching, TLS termination, origin connectivity |
| AWS Shield | DDoS protection |
| AWS WAF | HTTP request inspection and filtering |
| Origin | Application and business logic |

AWS WAF is therefore not a replacement for CloudFront or Shield. It is the application-layer control placed in front of the workload.

## Why AWS WAF Matters

A network-level DDoS protection system can help absorb large amounts of malicious traffic, but an application can still be attacked with requests that are syntactically valid HTTP.

For example:

```http
POST /login HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"username":"alice","password":"..."}
```

The request may be perfectly valid from an HTTP perspective while still being part of:

- Credential attacks
- Bot traffic
- Scraping
- HTTP floods
- Request abuse
- SQL injection attempts
- Cross-site scripting attempts
- Path traversal attempts
- Excessive API consumption

WAF allows security policies to reason about the characteristics of HTTP requests before they consume application resources.

## WAF in a CloudFront Architecture

For a public backend:

```mermaid
flowchart LR
    C[Client]
    CF[CloudFront]
    W[AWS WAF]
    ALB[Application Load Balancer]
    APP[Django / FastAPI]
    DB[(PostgreSQL)]
    R[(Redis)]

    C --> CF
    CF --> W
    W --> ALB
    ALB --> APP
    APP --> DB
    APP --> R
```

The architectural objective is to reject undesirable requests as early as practical.

```text
Internet
   │
   ▼
CloudFront
   │
   ▼
WAF
   │
   ├── Reject malicious traffic
   │
   └── Forward acceptable traffic
             │
             ▼
           Origin
```

The farther a request travels into the architecture, the more resources it can consume.

## What WAF Can Inspect

WAF rules can inspect characteristics of HTTP requests such as:

- Source IP address
- HTTP method
- URI path
- Query string
- Headers
- Cookies
- Request body
- Labels generated by other rules
- Geographic origin
- Rate of requests
- Known malicious patterns

The exact fields available depend on the rule statement and AWS WAF feature being used.

A request can therefore be evaluated using multiple dimensions:

```text
Request
  │
  ├── IP address
  ├── HTTP method
  ├── URI
  ├── Query string
  ├── Headers
  ├── Cookies
  ├── Body
  └── Request rate
        │
        ▼
      WAF Rules
        │
        ▼
      Action
```

## Web ACL

A Web ACL is the main policy object used to associate WAF rules with a protected resource.

For CloudFront, the Web ACL is associated with the CloudFront distribution.

Conceptually:

```text
CloudFront Distribution
        │
        ▼
     Web ACL
        │
        ├── Rule A
        ├── Rule B
        ├── Rule C
        └── Rule D
```

A Web ACL contains:

- Rules
- Rule priorities
- Default action
- Visibility configuration
- Optional managed rule groups
- Optional custom statements and actions

The Web ACL should represent the security policy for the protected application rather than becoming an unstructured collection of unrelated rules.

## Default Action

A Web ACL has a default action that determines what happens when no rule produces a terminating decision.

Common actions include:

- `ALLOW`
- `BLOCK`

A common production model is:

```text
Default action: ALLOW

Known malicious request
        │
        ▼
      BLOCK

Known abusive pattern
        │
        ▼
      BLOCK

Normal request
        │
        ▼
      ALLOW
```

A default-allow strategy is often easier to operate for public applications because only known undesirable patterns are blocked.

A default-block strategy can be appropriate for tightly controlled APIs, administrative interfaces, or allowlisted systems, but it requires explicit modeling of every legitimate traffic source.

## Rule Evaluation

Rules in a Web ACL are evaluated according to their configured priority.

Conceptually:

```text
Request
  │
  ▼
Rule 1
  │
  ├── Terminating action ──► Stop
  │
  └── No terminating action
             │
             ▼
           Rule 2
             │
             ▼
           Rule 3
             │
             ▼
      Default action
```

This means rule ordering is an architectural concern.

A broad blocking rule placed before a specific exception can prevent the exception from being evaluated.

## WAF Actions

Common WAF actions include:

| Action | Purpose |
|---|---|
| Allow | Explicitly permit the request |
| Block | Reject the request |
| Count | Record a match without blocking |
| CAPTCHA | Require a CAPTCHA challenge |
| Challenge | Require a browser challenge |

### Allow

Use `ALLOW` when a request should explicitly bypass subsequent rule processing.

Typical use cases include:

- Trusted internal integrations
- Specific administrative access paths
- Carefully controlled exceptions

Allow rules should be narrow.

### Block

`BLOCK` terminates processing and rejects the request.

Typical use cases:

- Known malicious IPs
- Malicious request patterns
- Disallowed geographic traffic
- Excessive request rates
- Known exploit signatures

### Count

`COUNT` is especially useful during rule rollout.

Instead of:

```text
Request
  │
  ▼
New rule
  │
  ▼
BLOCK
```

start with:

```text
Request
  │
  ▼
New rule
  │
  ▼
COUNT
  │
  ▼
Application
```

This allows the team to measure potential false positives before enforcing the rule.

### CAPTCHA and Challenge

Challenge-based actions can help distinguish automated traffic from legitimate browser clients.

They are useful when a request should not immediately be blocked but should demonstrate additional evidence of legitimacy.

They are less appropriate for APIs consumed by non-browser clients because a machine-to-machine client may not be able to complete the expected interaction.

## Managed Rule Groups

AWS WAF supports managed rule groups that provide prebuilt protections for common web application attack patterns.

They can reduce the amount of custom rule logic required for common threats.

Typical protection categories include:

- Common web exploits
- Known malicious patterns
- IP reputation
- Anonymous or suspicious sources
- Bot-related traffic

Managed rules should not be enabled blindly.

A rule group can produce false positives against legitimate application traffic, especially when an API accepts complex payloads or unusual request patterns.

Production rollout should therefore use:

```text
Enable
  │
  ▼
Count / observe
  │
  ▼
Inspect matches
  │
  ▼
Tune exclusions
  │
  ▼
Move selected rules to blocking
```

## Custom Rules

Custom rules are appropriate when the application's traffic model is known.

Examples:

```text
Block:
    /admin/* from untrusted networks

Rate-limit:
    /login

Allow:
    trusted integration IPs

Block:
    requests containing known malicious patterns

Challenge:
    suspicious browser traffic
```

Custom rules should be based on application behavior rather than arbitrary assumptions.

## IP-Based Filtering

WAF can filter traffic based on IP addresses through IP sets and related rule statements.

A common pattern is:

```text
Known malicious IPs
       │
       ▼
    IP Set
       │
       ▼
     WAF
       │
       ▼
     BLOCK
```

IP-based blocking is useful but limited.

Attackers can:

- Rotate IP addresses.
- Use cloud infrastructure.
- Use residential proxies.
- Use botnets.
- Distribute traffic globally.

Therefore, IP filtering should rarely be the only security mechanism.

## Geographic Filtering

WAF can apply geographic conditions to requests.

For example:

```text
Request
   │
   ▼
Country condition
   │
   ├── Allowed geography ──► Continue
   │
   └── Restricted geography ► Block
```

Geo restrictions are useful when the business has a clear geographic access requirement.

They are dangerous when geographic assumptions are weak.

For example, blocking traffic from a country does not necessarily identify the actual user location because clients can use VPNs, proxies, and other intermediaries.

Use geographic filtering as a business/security control, not as a reliable identity mechanism.

## URI Path Filtering

URI-based rules are useful for protecting specific application endpoints.

Example:

```text
/api/login
/api/password-reset
/api/search
/api/reports
/api/admin/*
```

Different endpoints often have different security and capacity characteristics.

For example:

| Endpoint | Typical protection |
|---|---|
| `/health` | Minimal filtering |
| `/login` | Rate limiting + bot controls |
| `/password-reset` | Rate limiting + abuse controls |
| `/search` | Rate limiting + request validation |
| `/reports` | Authentication + aggressive rate controls |
| `/admin/*` | Strong authentication + restrictive access |

This is more precise than applying one global rate limit to every request.

## HTTP Method Filtering

Applications should explicitly define which methods each endpoint supports.

For example:

```text
GET     /api/products
POST    /api/orders
PATCH   /api/orders/{id}
DELETE  /api/orders/{id}
```

Unexpected methods can be rejected at the application or WAF layer where appropriate.

However, WAF method filtering should not replace application routing and authorization.

The backend must still validate:

- HTTP method
- Authentication
- Authorization
- Resource ownership
- Request schema

## Header Filtering

Headers can provide useful signals.

Examples include:

- `User-Agent`
- `Referer`
- Custom application headers
- Forwarded headers
- Authorization-related metadata

However, HTTP headers are client-controlled unless they are cryptographically authenticated or generated by a trusted intermediary.

Do not treat:

```http
User-Agent: InternalService
```

as proof that the request came from an internal service.

A malicious client can send the same header.

## Query String Filtering

Query strings are often useful for detecting suspicious requests:

```text
/search?q=...
/products?id=...
/redirect?url=...
```

Potential security concerns include:

- Injection attempts
- Unexpected parameters
- Excessive parameter sizes
- Cache-key manipulation
- Open redirect abuse

WAF can inspect query-string content, but application-level validation remains mandatory.

## Request Body Inspection

For APIs, request bodies can contain malicious payloads.

For example:

```json
{
  "username": "alice",
  "comment": "<script>...</script>"
}
```

or:

```json
{
  "search": "' OR 1=1 --"
}
```

WAF can identify certain known attack signatures.

However:

> WAF is an additional security layer, not a substitute for parameterized SQL, output encoding, schema validation, and secure application development.

A Django application should still use Django ORM or parameterized database operations rather than constructing SQL through string concatenation.

## SQL Injection Protection

SQL injection occurs when attacker-controlled input changes the structure of a SQL statement.

Unsafe application logic can conceptually create:

```text
SQL = "SELECT * FROM users WHERE name = '" + user_input + "'"
```

The primary defense is parameterized database access.

For Django:

```python
from django.contrib.auth.models import User

user = User.objects.filter(username=username).first()
```

WAF can provide another layer by detecting common injection signatures, but the application must remain secure even if WAF is bypassed or misconfigured.

## Cross-Site Scripting

XSS attacks attempt to inject executable browser-side content.

For example:

```html
<script>alert("x")</script>
```

WAF managed rules can detect common XSS patterns, but application security remains essential.

Backend teams should use:

- Context-aware output encoding
- Safe templating
- Content Security Policy where appropriate
- Input validation
- Secure cookie configuration
- Framework security controls

Do not assume that blocking obvious `<script>` strings completely solves XSS.

## Rate-Based Rules

Rate-based rules are one of the most important WAF controls for public APIs.

Conceptually:

```text
Client
  │
  ├── Request 1
  ├── Request 2
  ├── Request 3
  ├── ...
  └── Excessive requests
             │
             ▼
       Rate-based rule
             │
             ▼
       Control / Block
```

They are useful for:

- Login endpoints
- Password reset
- OTP generation
- Search
- Expensive APIs
- Public resource creation
- Authentication endpoints

The threshold should reflect actual application behavior.

An arbitrary value such as "100 requests per minute" may be inappropriate without understanding legitimate traffic.

## Rate Limiting vs Throttling

The terms are often used interchangeably, but the implementation location matters.

### WAF rate-based control

Operates at the edge.

```text
Client
  │
  ▼
CloudFront
  │
  ▼
WAF
  │
  └── Rate control
```

### Application throttling

Operates inside the backend.

```text
Client
  │
  ▼
CloudFront
  │
  ▼
WAF
  │
  ▼
Django / FastAPI
  │
  └── Application throttle
```

A strong production architecture can use both.

WAF provides coarse edge protection while application throttling can enforce user-, API-key-, tenant-, or business-specific limits.

## WAF and Django REST Framework

Django REST Framework provides application-level throttling mechanisms.

A layered architecture can therefore look like:

```text
Internet
   │
   ▼
CloudFront
   │
   ▼
AWS WAF
   │
   ├── Global traffic controls
   ├── IP-based rules
   └── Rate-based rules
   │
   ▼
Django / DRF
   │
   ├── Authentication
   ├── Permissions
   ├── DRF throttling
   └── Validation
```

The controls solve different problems.

WAF does not understand:

```text
"user_123 has exceeded their monthly API quota"
```

DRF or application middleware can enforce such business-specific rules.

## WAF and FastAPI

FastAPI applications can similarly implement application-level controls after WAF.

For example:

```text
CloudFront
    │
    ▼
WAF
    │
    ▼
FastAPI
    │
    ├── Authentication
    ├── Authorization
    ├── Pydantic validation
    └── Business-level rate limits
```

Pydantic validation protects application semantics, while WAF protects at the HTTP edge.

## WAF and Microservices

WAF should generally protect the public entry point rather than attempting to become a replacement for internal service authorization.

Example:

```text
Internet
   │
   ▼
CloudFront
   │
   ▼
WAF
   │
   ▼
API Gateway / ALB
   │
   ▼
Service A
   │
   ├── Service B
   ├── Service C
   └── Service D
```

Internal services should still enforce:

- Authentication between services
- Authorization
- mTLS or equivalent controls where required
- Network policies
- Input validation
- Service-level quotas

WAF is not a substitute for zero-trust service-to-service security.

## Bot Traffic

Automated clients are not automatically malicious.

Examples of legitimate bots include:

- Search engine crawlers
- Monitoring systems
- Internal automation
- Partner integrations

Therefore:

```text
Bot traffic
   │
   ├── Legitimate ──► Allow
   │
   └── Malicious ───► Block / Challenge
```

A production bot strategy should avoid simplistic rules such as:

```text
User-Agent contains "bot" → BLOCK
```

because legitimate and malicious automation can both contain bot-like identifiers.

## Managed Bot Controls

For applications with significant automated traffic, AWS WAF provides bot-related capabilities that can help distinguish and manage automated clients.

Use cases include:

- Scraping protection
- Credential abuse
- Automated content consumption
- Inventory hoarding
- Automated form submissions

Bot protection can have a significant impact on legitimate clients if configured too aggressively.

Monitor first, then enforce.

## Allowlisting

Allowlisting means explicitly permitting known traffic sources.

For example:

```text
Partner API
    │
    ▼
Known IP ranges
    │
    ▼
WAF IP Set
    │
    ▼
Allow
```

Allowlisting is useful for:

- Partner APIs
- Administrative systems
- Internal integrations
- Controlled automation

It becomes difficult when clients use dynamic IP ranges.

For internet-facing applications, identity-based authentication is usually more robust than relying solely on source IP.

## Blocking by IP Is Not Identity

This is a common security mistake.

Consider:

```text
User A ──► NAT ──► Public IP
User B ──► NAT ──► Same Public IP
```

Blocking the IP can block both users.

Similarly:

```text
Attacker A ──► Proxy 1
Attacker B ──► Proxy 2
Attacker C ──► Proxy 3
```

means blocking one IP may have limited value.

Use IP filtering as one signal among multiple controls.

## Rule Priority and Exceptions

Suppose the following rules exist:

```text
Rule 1: Block country X
Rule 2: Allow trusted partner
```

If the partner is physically located in country X and Rule 1 terminates processing before Rule 2, the partner may still be blocked.

A more intentional policy might be:

```text
Rule 1: Allow trusted partner
Rule 2: Block country X
Rule 3: Block malicious IPs
```

The correct ordering depends on the desired security policy.

Always model exceptions explicitly.

## Managed Rules and False Positives

Security rules are imperfect.

A legitimate API request may accidentally match a generic attack signature.

For example:

```json
{
  "filter": "name=select"
}
```

could contain a token that resembles a SQL injection pattern even though the application legitimately supports it.

A production workflow should be:

```text
New WAF rule
    │
    ▼
Count
    │
    ▼
Observe metrics
    │
    ▼
Inspect sampled requests
    │
    ▼
Identify false positives
    │
    ▼
Tune scope / exclusions
    │
    ▼
Block
```

Do not disable an entire managed rule group because one rule generated false positives.

Where supported, narrow the exception to the smallest possible scope.

## Logging and Visibility

WAF visibility is essential for production operations.

Monitor:

- Allowed requests
- Blocked requests
- Counted requests
- Rule matches
- Rate-limit matches
- CAPTCHA/challenge actions
- Source distribution
- Targeted URI paths
- HTTP methods
- Response behavior

A useful operational dashboard correlates WAF metrics with CloudFront and origin metrics.

```text
WAF blocked requests     ↑
        │
        ├──────────────► CloudFront traffic
        │
        ├──────────────► Origin request count
        │
        ├──────────────► API latency
        │
        └──────────────► 5xx errors
```

## Sampled Requests

AWS WAF provides sampled request visibility that can help during rule tuning.

Sampling is useful for answering:

- Which requests match this rule?
- Which IPs are involved?
- Which URI is being targeted?
- Is legitimate traffic being blocked?
- Which headers or parameters are present?

Sampling should not be treated as a complete traffic log.

For forensic and compliance requirements, configure appropriate logging and retention separately.

## WAF Logging

A production logging architecture might look like:

```text
CloudFront
    │
    ├── Access logs
    │
    ▼
WAF
    │
    ├── WAF logs
    │
    ▼
Logging destination
    │
    ├── S3
    ├── CloudWatch Logs
    └── Security analytics pipeline
```

The exact destination and retention policy should be selected according to operational, compliance, and cost requirements.

## Monitoring and Alerting

Useful alerts include:

| Signal | Possible interpretation |
|---|---|
| Sudden blocked-request spike | Attack or overly aggressive rule |
| Sudden allowed-request spike | Legitimate traffic or attack |
| Rate-limit matches increase | Abuse or traffic surge |
| Specific rule suddenly dominates | New attack pattern or false positive |
| Origin traffic increases while WAF blocks increase | Some attack traffic is still passing |
| Origin CPU increases without proportional legitimate traffic | Application-layer abuse |
| 5xx increases after WAF deployment | Possible rule/configuration problem |

Do not alert on a single metric in isolation.

Correlate edge, WAF, origin, and business signals.

## Security Rules for APIs

A production API may use rules such as:

```text
Rule: Block known malicious IPs
Rule: Managed common attack protections
Rule: Rate-limit /login
Rule: Rate-limit /password-reset
Rule: Rate-limit /search
Rule: Restrict administrative paths
Rule: Block invalid HTTP methods where appropriate
Rule: Apply bot controls to public content
```

The exact policy should be derived from the application's threat model.

## Protecting Authentication Endpoints

Authentication endpoints deserve special attention because they are often both expensive and security-sensitive.

For example:

```text
POST /login
POST /register
POST /password-reset
POST /otp
```

An attacker can generate large numbers of requests against these endpoints.

A layered design is:

```text
Client
  │
  ▼
CloudFront
  │
  ▼
WAF
  │
  ├── Rate controls
  ├── Bot controls
  └── IP reputation
  │
  ▼
Application
  │
  ├── Authentication
  ├── Account controls
  ├── MFA
  └── Application throttling
```

The application must still enforce account-level protections because WAF generally does not understand the identity and state of a specific account.

## Protecting Expensive Endpoints

Suppose:

```http
GET /api/reports/annual
```

causes:

```text
API
 │
 ▼
PostgreSQL
 │
 ├── Large joins
 ├── Aggregation
 └── Sorting
```

A small number of clients can cause substantial backend load.

Use endpoint-specific controls:

```text
/api/reports/*
       │
       ▼
WAF rate rule
       │
       ▼
Authentication
       │
       ▼
Application quota
       │
       ▼
Cached / asynchronous processing
```

Where possible, cache report results or process them asynchronously with Celery rather than performing expensive work synchronously for every request.

## WAF and Cache Interaction

CloudFront caching can prevent requests from reaching the origin, but WAF operates as part of the CloudFront request processing path.

A simplified model is:

```text
Client
  │
  ▼
CloudFront
  │
  ▼
WAF evaluation
  │
  ├── Block ──► Reject
  │
  └── Continue
        │
        ▼
   Cache processing
        │
        ├── Hit ──► Edge response
        │
        └── Miss ─► Origin
```

This makes WAF particularly useful for protecting both cached and origin-bound requests.

## WAF and Cache-Key Abuse

Attackers may intentionally vary query parameters:

```text
/api/products?x=1
/api/products?x=2
/api/products?x=3
...
```

If these values create unique cache keys, cache efficiency can decrease.

This can turn:

```text
Cache hit
   │
   ▼
Edge response
```

into:

```text
Cache miss
   │
   ▼
Origin
   │
   ▼
Database
```

WAF and cache-key design should therefore be reviewed together for high-value public APIs.

## Protecting the Origin

The strongest architecture prevents attackers from bypassing WAF by connecting directly to the origin.

Preferred:

```text
Internet
   │
   ▼
CloudFront
   │
   ▼
WAF
   │
   ▼
Origin
```

Avoid:

```text
Internet ─────► CloudFront ───► Origin
   │
   └──────────────────────────► Origin
```

If the origin is directly accessible, an attacker can potentially bypass:

- CloudFront
- WAF
- Edge caching
- Edge traffic controls

Origin access should therefore be treated as part of the WAF architecture.

## Security Headers

WAF is not primarily responsible for implementing all browser security controls.

Security headers may be configured through CloudFront response headers policies or the application.

Relevant headers can include:

```text
Strict-Transport-Security
Content-Security-Policy
X-Content-Type-Options
Referrer-Policy
Permissions-Policy
```

The exact policy should match the application.

For example, a strict Content Security Policy can require application changes and should not be copied blindly into production.

## HTTPS and WAF

WAF protects HTTP(S) requests, while CloudFront provides the edge TLS termination layer.

A typical request path is:

```text
Browser
  │
  │ TLS
  ▼
CloudFront
  │
  │ HTTP request inspection
  ▼
WAF
  │
  ▼
Origin
```

TLS protects traffic in transit, while WAF determines whether the HTTP request should be permitted.

These are complementary controls.

## Infrastructure as Code

WAF configuration should be managed through infrastructure as code in production.

For example:

```text
Terraform / CloudFormation
          │
          ▼
Web ACL
          │
          ├── Managed rule groups
          ├── Custom rules
          ├── Rate-based rules
          ├── IP sets
          └── Logging
```

This provides:

- Version control
- Peer review
- Repeatability
- Environment consistency
- Auditable changes
- Easier rollback

Avoid manually creating critical WAF rules in the console without recording the resulting configuration in source control.


The exact thresholds and rule configuration must be adapted to the application's traffic patterns and current AWS WAF provider capabilities.

## Deployment Strategy

WAF changes should follow the same engineering discipline as application changes.

Recommended workflow:

```text
Rule change
    │
    ▼
Code review
    │
    ▼
Non-production validation
    │
    ▼
Count / observe
    │
    ▼
Production rollout
    │
    ▼
Monitor
    │
    ▼
Enforce
```

Avoid deploying large collections of blocking rules immediately before a major production event.

## CI/CD Integration

A production pipeline can manage WAF changes alongside the infrastructure stack:

```text
Developer
   │
   ▼
Git commit
   │
   ▼

   │
   ├── Terraform validation
   ├── Policy validation
   └── Security checks
   │

   │
   ▼

   │
   ▼

   │
   ▼

```

This allows WAF configuration to receive the same review and change-control discipline as application infrastructure.

## Common Mistakes and Pitfalls

### Treating WAF as a Complete Security Boundary

**Problem:** The team assumes WAF makes the application secure.

**Why it happens:** WAF provides visible security controls at the edge.

**Correction:** Continue enforcing authentication, authorization, validation, secure database access, and secure application design.

### Blocking Everything Suspicious

**Problem:** Broad rules generate false positives.

**Correction:** Start with `COUNT`, analyze matches, narrow the rule, then enforce.

### Using IP Address as Identity

**Problem:** Multiple users may share one public IP.

**Correction:** Use authentication and application-level identity controls for user-specific policies.

### Relying Only on IP Blocking

**Problem:** Attackers can rotate IP addresses.

**Correction:** Combine IP reputation, rate controls, bot controls, managed rules, and application protections.

### Applying One Rate Limit Globally

**Problem:** Cheap endpoints and expensive endpoints have different capacity characteristics.

**Correction:** Use scope-down statements and endpoint-specific policies where appropriate.

### Ignoring Rule Priority

**Problem:** An earlier terminating rule prevents a later exception from being evaluated.

**Correction:** Design rule ordering explicitly and test exceptions.

### Enabling Managed Rules Without Monitoring

**Problem:** Legitimate traffic gets blocked.

**Correction:** Observe matches first and tune false positives before enforcing.

### Allowlisting Broad IP Ranges

**Problem:** A trusted IP range may contain systems that should not have unrestricted access.

**Correction:** Combine network restrictions with authentication and authorization.

### Assuming WAF Stops DDoS

**Problem:** Large network-level attacks are outside the primary scope of application-layer WAF filtering.

**Correction:** Use AWS Shield and CloudFront for DDoS resilience and WAF for HTTP-level filtering.

### Forgetting Direct-Origin Access

**Problem:** Attackers bypass CloudFront and WAF.

**Correction:** Restrict origin access where practical.

## Production Best Practices

### Rule Design

- Keep rules narrowly scoped.
- Give rules descriptive names.
- Document the security rationale.
- Avoid unnecessary rule duplication.
- Use priorities deliberately.
- Prefer reusable IP sets where appropriate.
- Keep exceptions as narrow as possible.

### Rollout

- Test rules outside production.
- Start new blocking logic in count mode where appropriate.
- Monitor false positives.
- Roll out incrementally.
- Maintain rollback capability.

### API Protection

- Rate-limit authentication endpoints.
- Protect expensive APIs.
- Enforce application-level quotas.
- Validate request bodies.
- Restrict unsupported HTTP methods.
- Require authentication where appropriate.

### Origin Protection

- Prevent direct-origin bypass.
- Use HTTPS between CloudFront and the origin.
- Restrict origin network access where possible.
- Do not expose unnecessary backend services publicly.

### Observability

- Enable WAF metrics.
- Monitor rule matches.
- Centralize logs where appropriate.
- Correlate WAF events with CloudFront and origin metrics.
- Alert on unusual changes rather than static thresholds alone.

### Change Management

- Store WAF configuration in source control.
- Use infrastructure as code.
- Require peer review.
- Test before production.
- Record security exceptions.

## Interview Traps

### Is AWS WAF a DDoS Protection Service?

Not primarily. WAF provides application-layer HTTP request filtering. AWS Shield provides managed DDoS protection.

### Does WAF Protect a Public Application Without CloudFront?

WAF can protect supported AWS resources independently, but for a CloudFront architecture, associating the Web ACL with CloudFront places the filtering policy at the edge.

### Can WAF Replace Authentication?

No. WAF can filter traffic based on request characteristics but should not replace application identity and authorization controls.

### Can WAF Detect Every SQL Injection?

No. WAF managed rules can detect common attack patterns, but secure parameterized database access remains mandatory.

### Should Every WAF Rule Block Immediately?

No. Count mode is valuable for observing potential matches and identifying false positives before enforcement.

### Does WAF Know Whether a User Is Legitimate?

Not inherently. It evaluates request characteristics and configured signals. User identity and business context generally remain application responsibilities.

### Should Rate Limiting Be Done Only in WAF?

No. WAF provides edge-level controls, while application-level rate limiting can enforce user-, tenant-, API-key-, or business-specific policies.

### Why Does Rule Priority Matter?

Because terminating actions can stop further rule evaluation. An incorrectly ordered rule can prevent a legitimate exception from being reached.

### Does WAF Protect the Origin if the Origin Is Public?

It protects traffic passing through the protected WAF path. If attackers can directly access the origin, they can potentially bypass that path.

## Key Takeaways

- **AWS WAF is the HTTP/application-layer filtering component of a CloudFront security architecture; it complements CloudFront and AWS Shield rather than replacing them.**
- **Use layered controls: managed rules for common threats, custom rules for application-specific behavior, rate-based rules for abuse, and application-level authentication and authorization for business security.**
- **Treat WAF rule ordering, false-positive management, and rollout strategy as production engineering concerns; use count mode and observability before broadly blocking legitimate traffic.**
- **Protect high-cost endpoints and prevent direct-origin bypasses so malicious traffic cannot simply move past the edge and consume backend resources.**
- **Manage WAF configuration through infrastructure as code and CI/CD so security policies are versioned, reviewed, repeatable, and auditable.**
