# 02- HTTPS and TLS

## Overview

HTTPS and TLS are fundamental to a secure CloudFront deployment. CloudFront sits between viewers and origins, so transport security must be considered across two independent connections:

```text
Viewer
  │
  │ HTTPS / TLS
  ▼
CloudFront
  │
  │ HTTPS / TLS
  ▼
Origin
```

The first TLS connection protects communication between the client and CloudFront. The second protects communication between CloudFront and the origin.

These connections have separate certificates, protocol negotiation, trust relationships, and operational considerations. Enabling HTTPS for viewers therefore does **not** automatically mean that the origin connection is encrypted.

For production systems, TLS should be treated as an end-to-end architectural concern:

```mermaid
flowchart LR
    C[Browser / API Client]
    CF[CloudFront]
    O[Origin]
    A[Django / FastAPI]

    C -->|HTTPS + TLS| CF
    CF -->|HTTPS + TLS| O
    O --> A
```

The goal is not simply to "turn on HTTPS". The goal is to establish a deliberate trust boundary and encrypted transport path from the client to the application origin.

## HTTPS and TLS Fundamentals

### What TLS Provides

TLS provides:

- Encryption
- Server authentication
- Integrity protection
- Protection against passive network interception
- Protection against modification of traffic in transit

HTTPS is HTTP transported over TLS.

```text
HTTP
  +
TLS
  =
HTTPS
```

TLS does not provide application authorization.

For example, TLS can establish:

```text
"This client is communicating securely with api.example.com."
```

It does not establish:

```text
"This authenticated user is authorized to delete order #123."
```

That decision remains an application responsibility.

### Why CloudFront Uses TLS

CloudFront terminates TLS at the edge so that clients can securely communicate with the globally distributed CloudFront service.

The basic flow is:

```text
Client
  │
  │ 1. DNS resolves CloudFront hostname
  │
  │ 2. TCP connection
  │
  │ 3. TLS handshake
  │
  ▼
CloudFront Edge
  │
  │ 4. HTTP request
  │
  ▼
Cache / Origin
```

CloudFront can then inspect the HTTP request, apply configured policies, consult the cache, and potentially forward the request to the origin.

## Viewer-Side TLS

Viewer-side TLS protects the client-to-CloudFront connection.

```text
Client
   │
   │ HTTPS
   ▼
CloudFront Edge
```

This is the connection users normally see in their browser:

```text
https://www.example.com
```

The CloudFront distribution uses a certificate that covers the hostname being requested.

For example:

```text
www.example.com
api.example.com
static.example.com
```

can be associated with appropriate CloudFront distributions and certificates according to the application's architecture.

## TLS Certificate

A TLS certificate binds a domain name to a public key and provides information that allows the client to verify the server's identity.

Conceptually:

```text
Certificate
├── Domain identity
├── Public key
├── Validity period
├── Issuer
└── Signature
```

A browser validates the certificate chain and hostname before establishing trust.

### Certificate Requirements

For a production CloudFront hostname, the certificate must:

- Cover the requested hostname.
- Be valid and not expired.
- Be trusted by supported clients.
- Be associated with CloudFront correctly.
- Be maintained through its lifecycle.

For AWS-managed certificates, AWS Certificate Manager is typically used.

## AWS Certificate Manager and CloudFront

CloudFront certificates are associated with the distribution rather than generated by CloudFront itself.

A common architecture is:

```text
AWS Certificate Manager
          │
          │ Certificate
          ▼
     CloudFront
          │
          ▼
        Origin
```

For CloudFront distributions, certificates used for viewer HTTPS are associated with ACM in the **US East (N. Virginia) region (`us-east-1`)**.

This is an important operational distinction because CloudFront is a global service while ACM certificates are regional resources.

### Production Consideration

A common deployment mistake is requesting the certificate in the application's primary AWS region and then being unable to select it for CloudFront.

For example:

```text
Application infrastructure:
ap-south-1

CloudFront viewer certificate:
us-east-1
```

The application region and CloudFront certificate region do not need to be the same.

## Custom Domain Names

CloudFront distributions commonly use custom domain names.

For example:

```text
Client
  │
  │ https://api.example.com
  ▼
CloudFront
```

DNS must direct the custom hostname to the CloudFront distribution.

Conceptually:

```text
api.example.com
       │
       ▼
CloudFront distribution
       │
       ▼
Origin
```

The certificate must also cover `api.example.com`.

DNS and TLS therefore need to be configured as a pair:

| Component | Responsibility |
|---|---|
| DNS | Routes the hostname to CloudFront |
| Certificate | Establishes TLS identity for the hostname |
| CloudFront | Terminates viewer TLS |
| Origin | Handles the backend request |

## TLS Handshake

A simplified TLS handshake looks like:

```mermaid
sequenceDiagram
    participant C as Client
    participant CF as CloudFront

    C->>CF: ClientHello
    CF->>C: ServerHello + Certificate
    C->>CF: Key exchange / handshake messages
    CF->>C: Handshake completion
    C->>CF: Encrypted HTTP request
    CF-->>C: Encrypted HTTP response
```

The exact handshake differs by TLS version and cryptographic configuration, but the engineering goal remains the same:

1. Negotiate protocol parameters.
2. Authenticate the server.
3. Establish shared cryptographic material.
4. Encrypt application traffic.

## TLS Versions

TLS has evolved over time.

| Protocol | Production Recommendation |
|---|---|
| SSLv2 | Do not use |
| SSLv3 | Do not use |
| TLS 1.0 | Obsolete |
| TLS 1.1 | Obsolete |
| TLS 1.2 | Widely supported and production-grade |
| TLS 1.3 | Modern protocol where supported |

Production CloudFront configurations should use modern TLS policies appropriate for the application's compatibility requirements.

Avoid supporting obsolete protocol versions merely because an old client might still exist unless there is a documented business requirement and compensating controls.

## Security Policies

CloudFront security policies control the TLS protocol versions and cryptographic settings accepted for viewer connections.

A stronger policy generally improves security but may reduce compatibility with old clients.

The decision should consider:

- Client population
- Browser support
- API consumers
- Mobile applications
- Internal enterprise clients
- Regulatory requirements
- Organizational security standards

A useful engineering rule is:

> Choose the strongest TLS policy compatible with the actual clients you must support.

Do not optimize for hypothetical legacy clients.

## Viewer Protocol Policy

CloudFront can control how HTTP and HTTPS viewer requests are handled.

Typical choices include:

| Policy | Behavior |
|---|---|
| HTTP and HTTPS | Both protocols accepted |
| Redirect HTTP to HTTPS | HTTP redirected to HTTPS |
| HTTPS only | HTTP requests rejected |

For public web applications, redirecting HTTP to HTTPS is commonly used:

```text
http://example.com
        │
        ▼
   CloudFront
        │
        ▼
301 / 307 redirect
        │
        ▼
https://example.com
```

For APIs, an explicit HTTPS-only policy can be preferable where clients should never receive an HTTP endpoint.

## HTTP-to-HTTPS Redirects

Redirecting HTTP requests provides compatibility while establishing HTTPS as the canonical endpoint.

Example:

```text
GET http://api.example.com/users
```

becomes:

```text
GET https://api.example.com/users
```

The redirect itself is not encrypted because the initial request used HTTP.

This matters for security-sensitive applications.

If credentials or sensitive information are sent over HTTP before the redirect occurs, those credentials are already exposed.

Therefore:

- Do not instruct clients to send credentials over HTTP.
- Prefer HTTPS endpoints in API documentation.
- Use HTTPS as the canonical application URL.
- Avoid relying on redirects as the primary security mechanism for sensitive requests.

## CloudFront-to-Origin TLS

Viewer TLS and origin TLS are separate.

Consider:

```text
Client
  │
  │ HTTPS
  ▼
CloudFront
  │
  │ HTTPS
  ▼
ALB / API / S3 / Custom Origin
```

CloudFront can communicate with supported origins using HTTPS.

This is particularly important when the origin processes sensitive data.

### Why Origin TLS Matters

Without encrypted origin communication:

```text
Client ── HTTPS ──► CloudFront ── HTTP ──► Origin
```

the CloudFront-to-origin segment is not protected by TLS.

With HTTPS:

```text
Client ── HTTPS ──► CloudFront ── HTTPS ──► Origin
```

both network segments use encrypted transport.

## End-to-End TLS

"End-to-end TLS" should be used carefully because CloudFront terminates the viewer TLS session and establishes a separate connection to the origin.

A more precise architecture is:

```text
TLS session #1
Client ─────────────────► CloudFront

TLS session #2
CloudFront ──────────────► Origin
```

CloudFront is therefore a TLS termination point.

This allows CloudFront to perform functions such as:

- HTTP request routing
- Cache lookup
- WAF integration
- Header processing
- Origin selection
- Response caching

The traffic remains encrypted on each network segment, but CloudFront is logically between the two TLS sessions.

## Origin Certificate Validation

When CloudFront connects to an HTTPS origin, the origin certificate must satisfy the expected certificate requirements.

Operationally, verify:

- The certificate is valid.
- The hostname matches the origin configuration.
- The certificate chain is trusted.
- The certificate is not expired.
- The origin supports the required TLS configuration.

A valid viewer certificate does not guarantee a valid origin certificate.

## SNI and Hostnames

Modern TLS commonly uses Server Name Indication (SNI) so that a client can communicate the hostname it intends to access during the TLS handshake.

This is important for systems hosting multiple HTTPS domains on shared infrastructure.

Conceptually:

```text
Client
  │
  │ ClientHello
  │ SNI = api.example.com
  ▼
CloudFront
  │
  ▼
Select appropriate certificate / configuration
```

SNI allows infrastructure to serve multiple hostnames without requiring a separate network endpoint for every hostname.

## CloudFront and API Backends

A typical API architecture is:

```text
Client
  │
  │ HTTPS
  ▼
CloudFront
  │
  │ HTTPS
  ▼
Application Load Balancer
  │
  ▼
Django / FastAPI
```

For example:

```text
https://api.example.com/users
```

can be routed through CloudFront to a backend service.

The backend may then execute:

```text
Authentication
      │
      ▼
Authorization
      │
      ▼
Business logic
      │
      ▼
PostgreSQL / Redis / Kafka
```

TLS protects the network transport but does not replace those application-level controls.

## TLS and Reverse Proxies

CloudFront often becomes the first proxy in a chain:

```text
Client
  │
  ▼
CloudFront
  │
  ▼
ALB
  │
  ▼
Nginx
  │
  ▼
Django / FastAPI
```

The application must understand that the original client request was HTTPS even though the backend may receive traffic through an internal HTTP or HTTPS hop.

Incorrect proxy configuration can cause issues such as:

- Incorrect redirect loops
- Incorrect absolute URLs
- Secure cookies not being recognized
- CSRF failures
- Incorrect request scheme detection

For Django, secure proxy and cookie settings should be configured according to the actual trusted proxy architecture.

Example:

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")

SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
```

Only configure trusted proxy headers when the network path guarantees that untrusted clients cannot forge the corresponding headers.

## TLS and Secure Cookies

TLS should be combined with secure cookie attributes for applications using session-based authentication.

A production session cookie should generally use:

```text
Secure
HttpOnly
SameSite
```

For example:

```http
Set-Cookie: sessionid=...; Secure; HttpOnly; SameSite=Lax
```

TLS protects the cookie while it is transmitted, while `Secure` prevents browsers from sending the cookie over HTTP.

`HttpOnly` reduces exposure to client-side JavaScript, and `SameSite` helps control cross-site cookie behavior.

These controls address different threats and should not be treated as interchangeable.

## TLS and APIs

For REST APIs:

```text
Client
   │
   │ HTTPS
   ▼
CloudFront
   │
   ▼
Django / FastAPI
```

API clients should use HTTPS for:

- Authentication
- Authorization headers
- API keys
- JWTs
- Session cookies
- Request payloads
- Response payloads

Never design an API around the assumption that authentication headers can safely traverse plaintext HTTP.

## TLS and gRPC

gRPC commonly uses HTTP/2 and TLS for secure transport.

A possible architecture is:

```text
Service A
   │
   │ gRPC + TLS
   ▼
CloudFront / Load Balancer / Internal Network
   │
   ▼
Service B
```

However, CloudFront should not automatically be inserted into every service-to-service gRPC architecture.

For internal microservice communication, an internal load balancer, service mesh, or direct service networking may be more appropriate.

CloudFront is primarily an internet-facing edge delivery service and should be selected based on the communication pattern rather than simply because TLS is required.

## TLS and WebSockets

WebSocket applications can use secure WebSockets:

```text
wss://example.com/socket
```

The connection begins with HTTPS/TLS and then upgrades to a WebSocket connection.

Conceptually:

```text
Client
  │
  │ TLS
  ▼
CloudFront
  │
  │ WebSocket connection
  ▼
Origin
```

Secure WebSockets are appropriate when the application requires encrypted real-time communication.

## TLS Performance

TLS introduces computational work during connection establishment, but modern systems are designed to make this cost manageable.

The main performance considerations are:

- Connection establishment
- Handshake frequency
- TLS session reuse
- Network latency
- Client connection behavior
- HTTP/2 or HTTP/3 support
- Edge proximity

CloudFront reduces network latency by terminating connections closer to viewers.

```text
Viewer
  │
  │ Short regional path
  ▼
CloudFront Edge
  │
  │ AWS network
  ▼
Origin
```

This is one reason edge termination can improve both security and user-perceived latency.

## TLS and HTTP/2

HTTP/2 provides:

- Multiplexed streams
- Header compression
- More efficient connection utilization
- Reduced need for multiple parallel TCP connections

For frontend workloads containing many resources:

```text
HTML
CSS
JS
Images
Fonts
```

HTTP/2 can improve connection efficiency compared with older HTTP/1.1 request patterns.

## TLS and HTTP/3

HTTP/3 uses QUIC over UDP and incorporates TLS 1.3 into the transport protocol.

Conceptually:

```text
HTTP/1.1 / HTTP/2
       │
       ▼
      TCP
       │
       ▼
      TLS

HTTP/3
       │
       ▼
      QUIC
       │
       ▼
   TLS 1.3
```

HTTP/3 can improve behavior on networks with:

- Packet loss
- High latency
- Mobile connectivity changes
- Variable network conditions

Whether it should be enabled depends on the supported clients and workload requirements.

## Certificate Lifecycle

TLS certificates have an operational lifecycle:

```mermaid
flowchart LR
    R[Request certificate]
    V[Validate domain]
    A[Associate with CloudFront]
    M[Monitor]
    U[Renew]
    X[Replace / Rotate]

    R --> V
    V --> A
    A --> M
    M --> U
    U --> M
    M --> X
```

Certificate management should be automated whenever possible.

Monitor:

- Expiration dates
- Validation state
- Association with distributions
- DNS validation records
- Deployment changes

Manual certificate renewal is an avoidable operational risk.

## Certificate Rotation

Certificate rotation should not require application downtime.

A production process should:

1. Request or provision the new certificate.
2. Validate domain ownership.
3. Associate the certificate with CloudFront.
4. Wait for distribution deployment.
5. Validate HTTPS from representative clients.
6. Retire the old certificate when no longer needed.

Use infrastructure-as-code where possible so that certificate associations are reproducible.

## Infrastructure as Code

CloudFront TLS configuration should be managed through infrastructure automation where appropriate.

A conceptual Terraform configuration may look like:

```hcl
resource "aws_cloudfront_distribution" "api" {
  enabled = true

  aliases = ["api.example.com"]

  viewer_certificate {
    acm_certificate_arn      = aws_acm_certificate.api.arn
    ssl_support_method       = "sni-only"
    minimum_protocol_version = "TLSv1.2_2021"
  }

  # Origin and cache configuration omitted.
}
```

The exact TLS policy should be selected according to current AWS-supported policies and the application's client compatibility requirements.

## TLS Testing

Production validation should test the actual public hostname rather than only checking the CloudFront distribution configuration.

A basic OpenSSL check:

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com
```

Useful validation points include:

- Certificate subject
- Certificate issuer
- Expiration
- Certificate chain
- Negotiated TLS version
- Negotiated cipher
- SNI behavior

For HTTP-level validation:

```bash
curl -I https://api.example.com
```

For redirect testing:

```bash
curl -I http://api.example.com
```

The goal is to verify actual runtime behavior rather than merely trusting infrastructure configuration.

## Monitoring and Observability

TLS failures should be observable.

Monitor:

| Signal | Why It Matters |
|---|---|
| TLS handshake failures | Detect compatibility or certificate problems |
| HTTP 4xx/5xx rates | Detect downstream application problems |
| Origin connection failures | Detect origin TLS or availability problems |
| Certificate expiration | Prevent outages |
| CloudFront distribution changes | Detect configuration drift |
| Redirect rates | Detect unexpected HTTP usage |
| Client compatibility errors | Detect unsupported TLS policies |

A certificate expiration alert is particularly important because an expired certificate can turn an otherwise healthy application into a complete outage.

## Security Considerations

### Use Modern TLS

Prefer modern TLS configurations and avoid obsolete protocol versions.

### Protect Private Keys

Certificate private keys are highly sensitive credentials.

Do not:

- Commit them to Git.
- Store them in application source code.
- Place them in Docker images.
- Put them in public object storage.
- Share them through chat or tickets.

Use managed certificate services whenever possible.

### Avoid Certificate Mismatches

A common failure looks like:

```text
Requested hostname:
api.example.com

Certificate:
www.example.com
```

The TLS connection may fail hostname validation even if the certificate itself is otherwise valid.

### Avoid Trusting Untrusted Forwarded Headers

A backend may receive headers such as:

```http
X-Forwarded-Proto: https
```

These headers should only be trusted when inserted by a trusted proxy path.

Otherwise an attacker may attempt to forge them.

## Common Mistakes and Pitfalls

### Requesting the CloudFront Certificate in the Wrong Region

**Problem:** The certificate cannot be associated with the distribution.

**Cause:** The certificate was provisioned outside `us-east-1`.

**Correction:** Use ACM in `us-east-1` for CloudFront viewer certificates.

### Enabling Viewer HTTPS but Leaving the Origin on HTTP

**Problem:** The viewer-to-edge connection is encrypted but the edge-to-origin connection is not.

**Correction:** Explicitly configure and validate the origin protocol.

### Using an Expired Certificate

**Problem:** Clients receive TLS failures.

**Cause:** Certificate lifecycle was handled manually.

**Correction:** Use managed renewal and expiration monitoring.

### Using an Incorrect Domain Name

**Problem:** Certificate hostname validation fails.

**Cause:** The certificate does not cover the requested hostname.

**Correction:** Ensure the certificate SANs cover all required CloudFront aliases.

### Assuming HTTPS Means the Application Is Secure

**Problem:** Developers treat transport encryption as authorization.

**Correction:** Keep authentication, authorization, input validation, and business security in the application.

### Trusting Forwarded HTTPS Headers From Clients

**Problem:** Application logic may incorrectly believe a request arrived securely.

**Correction:** Only trust proxy-generated forwarding headers when the network topology guarantees their integrity.

### Supporting Legacy TLS Without a Requirement

**Problem:** Security posture is weakened for hypothetical clients.

**Correction:** Establish actual compatibility requirements and use the strongest practical policy.

### Forgetting Secure Cookies

**Problem:** Session cookies may be sent over insecure connections.

**Correction:** Use secure cookie settings together with HTTPS.

### Ignoring Certificate Deployment Time

**Problem:** A deployment appears successful but the distribution has not finished propagating the configuration.

**Correction:** Treat CloudFront configuration changes as asynchronous infrastructure deployments and validate the deployed state before considering the change complete.

## HTTPS/TLS Decision Matrix

| Requirement | Recommended Approach |
|---|---|
| Public website | HTTPS with modern TLS |
| Public REST API | HTTPS with modern TLS |
| Private API | HTTPS where traffic crosses untrusted or shared networks |
| Static assets | HTTPS + long-lived caching where appropriate |
| Private downloads | HTTPS + signed URL/cookie when suitable |
| Sensitive API response | HTTPS + carefully controlled caching |
| CloudFront to ALB | HTTPS when origin transport encryption is required |
| CloudFront to custom origin | HTTPS with validated origin certificate |
| S3 private content | CloudFront HTTPS + private S3 access |
| Internal microservices | Evaluate private networking, mTLS, service mesh, or internal load balancing rather than automatically using CloudFront |
| Legacy clients | Document compatibility requirement before weakening TLS policy |

## Interview Traps

### Is HTTPS Between the Browser and CloudFront Enough?

No. CloudFront and the origin have a separate connection. If origin transport encryption is required, configure HTTPS for the origin connection as well.

### Where Must the CloudFront ACM Certificate Exist?

For CloudFront viewer certificates, the ACM certificate must be in `us-east-1`.

### Does CloudFront Use the Same TLS Connection to the Origin?

No. CloudFront terminates the viewer TLS session and establishes a separate origin connection.

### Does TLS Provide Authentication?

TLS provides server authentication at the transport layer. It does not authenticate application users or authorize application operations.

### Is HTTP-to-HTTPS Redirect Completely Secure?

The final connection is secure, but the initial HTTP request is not encrypted. Sensitive clients should use HTTPS directly.

### Does a Valid Certificate Guarantee Secure Application Behavior?

No. A valid certificate establishes transport identity and encryption; it does not prevent authorization bugs, cache leakage, injection vulnerabilities, or insecure business logic.

## Key Takeaways

- **CloudFront has separate TLS connections for viewer-to-edge and edge-to-origin traffic; configure and validate both independently.**
- **CloudFront viewer certificates are typically managed through ACM in `us-east-1`, and certificate lifecycle management should be automated and monitored.**
- **Use modern TLS policies, enforce HTTPS appropriately, and select compatibility settings based on real client requirements rather than hypothetical legacy support.**
- **TLS protects transport but does not replace application authentication, authorization, secure cookies, proxy-header validation, or backend security controls.**
- **Treat certificate rotation, origin TLS, deployment propagation, and runtime validation as production operational concerns rather than one-time configuration tasks.**
