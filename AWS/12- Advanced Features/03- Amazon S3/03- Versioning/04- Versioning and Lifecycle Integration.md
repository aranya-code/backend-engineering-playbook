# 04- Versioning and Lifecycle Integration

## Overview

Amazon S3 Versioning and S3 Lifecycle solve complementary storage-management problems.

S3 Versioning preserves multiple versions of an object when the same object key is overwritten or deleted. S3 Lifecycle automates transitions between storage classes, expiration of current objects, permanent deletion of noncurrent versions, and cleanup of expired delete markers.

Used together, these capabilities provide a configurable retention model that balances recoverability, storage cost, and operational requirements.

For example, a document-management platform might retain the latest document version in S3 Standard, transition historical versions to an archive storage class, retain a defined number of previous versions, and eventually permanently delete versions after the approved retention period.

Versioning does not automatically expire historical data, and Lifecycle expiration does not necessarily permanently delete versioned objects. The interaction between the two must be designed explicitly.

## Understand the Versioning and Lifecycle Relationship

### Current and noncurrent versions

In a versioning-enabled general purpose bucket, an object key can have one current version and zero or more noncurrent versions.

When an application uploads a new object using an existing key, S3 preserves the previous version and makes the new version current.

For example, a document stored under `documents/customer-123/contract.pdf` may have this history:

| Version ID | Status | Description |
|---|---|---|
| `v003` | Current | Latest uploaded document |
| `v002` | Noncurrent | Previous document |
| `v001` | Noncurrent | Original document |

Version IDs are generated by S3. The example IDs are illustrative.

Every retained version consumes storage and can incur storage charges. A lifecycle policy must therefore define how long previous versions remain available and whether they should transition to cheaper storage classes before expiration.

### How the features interact

| Operation or lifecycle action | Behavior in a versioning-enabled bucket |
|---|---|
| Upload an object using an existing key | Creates a new current version; the previous current version becomes noncurrent |
| Delete an object without specifying a version ID | Creates a delete marker as the current version |
| Transition current version | Changes the storage class of the current object version |
| Transition noncurrent version | Changes the storage class of a historical version |
| Expire current version | Normally creates a delete marker rather than permanently deleting the current data version |
| Expire noncurrent version | Permanently deletes the eligible historical version |
| Remove expired object delete marker | Permanently removes a delete marker when it is the only remaining version |

Lifecycle actions are asynchronous. Reaching a configured age threshold does not mean an object will be transitioned or deleted at that exact moment.

Reference: [S3 Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html).

## Design a Version Retention Policy

### Define retention requirements before configuring lifecycle rules

A retention policy should specify both the business requirement and the corresponding S3 behavior.

| Requirement | Recommended mechanism | Important consideration |
|---|---|---|
| Recover from accidental overwrites | S3 Versioning | Retain the required number or duration of historical versions |
| Keep recent historical versions immediately accessible | Versioning with current and noncurrent storage-class rules | Account for retrieval charges and minimum storage durations |
| Reduce the cost of historical versions | `NoncurrentVersionTransition` | Validate retrieval requirements before archiving |
| Permanently remove old historical versions | `NoncurrentVersionExpiration` | Deleted versions cannot be recovered from S3 |
| Automatically remove expired delete markers | `ExpiredObjectDeleteMarker` | Only eligible markers with no remaining object versions are removed |
| Retain data for a legally required period | Appropriate retention controls, potentially S3 Object Lock | Lifecycle configuration must not violate retention obligations |
| Clean up abandoned multipart uploads | `AbortIncompleteMultipartUpload` | This is separate from object-version retention |

Avoid using one retention period for every object population. Customer documents, temporary exports, application logs, and compliance archives often have different requirements.

### Separate recovery retention from business retention

Recovery retention controls how long historical versions remain available for rollback or recovery.

Business retention defines how long records must remain stored to satisfy application, contractual, regulatory, or operational requirements.

These policies may overlap, but they are not equivalent. A document may need to remain available for seven years even if only the latest three versions are retained.

Similarly, retaining three historical versions does not guarantee a minimum recovery period. An object overwritten repeatedly can accumulate several versions within minutes.

Prefer time-based retention when a minimum historical recovery period is a firm requirement. Add a version-count constraint only when limiting the number of retained versions is also appropriate.

## Configure Lifecycle Rules for Versioned Objects

### Enable versioning before relying on historical recovery

Inspect the bucket versioning configuration:

```bash
aws s3api get-bucket-versioning \
  --bucket "$BUCKET"
```

An empty `Status` response means versioning has not been enabled. `Enabled` means versioning is enabled, and `Suspended` means versioning is suspended.

To enable versioning:

```bash
aws s3api put-bucket-versioning \
  --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled
```

Versioning can be suspended after it has been enabled, but it cannot be returned to the never-enabled state. Suspending it does not remove historical versions.

Enable versioning before relying on it for recovery, and verify the configuration as part of infrastructure deployment and post-deployment testing.

### Understand current-version expiration

The `Expiration` action applies to the current version in a versioned bucket.

When the current version is a normal object version, an expiration rule normally creates a delete marker. The previous object version becomes noncurrent and remains stored.

Consider this rule:

```json
{
  "ID": "ExpireOldCurrentObjects",
  "Status": "Enabled",
  "Filter": {
    "Prefix": "temporary/"
  },
  "Expiration": {
    "Days": 30
  }
}
```

After the configured lifetime, S3 can create a delete marker for an eligible current object under `temporary/`. The previous data version is not automatically permanently deleted by this rule.

**Production implication:** If the requirement is permanent deletion after 30 days, configure noncurrent-version expiration as well, subject to the approved recovery and retention policy.

### Configure noncurrent-version expiration

Use `NoncurrentVersionExpiration` to permanently delete historical versions after they have been noncurrent for a specified number of days.

```json
{
  "Rules": [
    {
      "ID": "ExpireOldNoncurrentDocuments",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "documents/"
      },
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 90
      }
    }
  ]
}
```

The example makes eligible noncurrent versions under `documents/` permanently deletable after 90 days of being noncurrent.

This action is irreversible through ordinary S3 version history once the corresponding versions have been permanently deleted. Validate that the retention period supports business recovery requirements before deployment.

### Retain a number of newer noncurrent versions

S3 also supports retaining a specified number of newer noncurrent versions with `NewerNoncurrentVersions`.

For example:

```json
{
  "Rules": [
    {
      "ID": "RetainRecentDocumentHistory",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "documents/"
      },
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 365,
        "NewerNoncurrentVersions": 3
      }
    }
  ]
}
```

This rule requires both the age condition and the newer-version count condition to be exceeded before an eligible noncurrent version can be permanently deleted.

The count refers to newer **noncurrent** versions, not the current version. The configuration must include a `Filter` when `NewerNoncurrentVersions` is specified. The supported value is between 1 and 100.

Use a version-count limit when both age and history depth matter. Do not interpret this setting as a guarantee that every object will retain exactly three historical versions under every lifecycle condition.

Reference: [S3 Lifecycle examples for versioned buckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html).

## Combine Storage Transitions and Version Expiration

### Use separate policies for current and historical versions

Current versions and noncurrent versions often have different access patterns. A current object may serve an active application, whereas historical versions may only be retrieved during investigations or recovery.

A policy can transition the current version to Standard-IA after 90 days, transition noncurrent versions to Glacier Flexible Retrieval after 30 days of being noncurrent, and expire sufficiently old noncurrent versions.

Example `lifecycle.json`:

```json
{
  "Rules": [
    {
      "ID": "ArchiveCurrentDocuments",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "documents/"
      },
      "Transitions": [
        {
          "Days": 90,
          "StorageClass": "STANDARD_IA"
        }
      ]
    },
    {
      "ID": "ArchiveAndExpireHistoricalVersions",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "documents/"
      },
      "NoncurrentVersionTransitions": [
        {
          "NoncurrentDays": 30,
          "StorageClass": "GLACIER"
        }
      ],
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 365,
        "NewerNoncurrentVersions": 3
      }
    }
  ]
}
```

The example assumes the storage classes and transition timing are appropriate for the workload. Review the current service constraints and regional pricing before deploying it.

In this configuration:

- Current document versions remain in their initial storage class until the current-version transition applies.
- Eligible historical versions can transition to Glacier Flexible Retrieval after becoming noncurrent.
- Eligible historical versions can be permanently deleted after the specified age and newer-version conditions are met.

A historical version should not be moved to an archive class if it must remain instantly accessible for user-facing requests. Retrieval requirements must be reviewed before selecting a transition destination.

### Account for storage-class constraints

Transitions and expiration rules must be compatible with the source storage class, destination storage class, object size, and required minimum storage duration.

Evaluate:
- Minimum storage durations and early-deletion charges.
- Retrieval charges and restoration latency.
- Minimum billable object sizes.
- Transition request charges.
- Archive metadata overhead where applicable.
- Current-version and historical-version access patterns.

Do not assume that moving an object version to a cheaper storage class guarantees lower total cost.

## Manage Delete Markers Correctly

### Understand delete-marker creation

In a versioning-enabled bucket, a deletion request without a version ID normally creates a delete marker instead of permanently deleting the object data.

For example:

```bash
aws s3api delete-object \
  --bucket "$BUCKET" \
  --key "documents/customer-123/contract.pdf"
```

This operation normally creates a delete marker. It does not permanently delete existing historical versions.

A normal read of the key generally treats the current delete marker as the effective deletion of the object. Previous versions may still be available to callers with the required permissions.

### Remove expired object delete markers

An expired object delete marker is a delete marker with no remaining noncurrent object versions.

A lifecycle rule can automatically remove eligible expired delete markers:

```json
{
  "Rules": [
    {
      "ID": "CleanExpiredDocumentDeleteMarkers",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "documents/"
      },
      "Expiration": {
        "ExpiredObjectDeleteMarker": true
      }
    }
  ]
}
```

The rule cannot use a tag-based filter for the `ExpiredObjectDeleteMarker` action. It also cannot combine `ExpiredObjectDeleteMarker` with `Days` in the same `Expiration` action.

Keep this cleanup rule separate when current-version expiration and delete-marker cleanup have different requirements.

**Important:** Removing an expired delete marker does not delete historical data versions, because the marker is eligible for this action only when no noncurrent object versions remain.

Reference: [Managing S3 delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html).

## Apply Versioning and Lifecycle Policies Safely

### Inspect the existing lifecycle configuration

Before changing lifecycle policies, inspect the current configuration:

```bash
aws s3api get-bucket-lifecycle-configuration \
  --bucket "$BUCKET"
```

Review every existing rule for:
- Scope and filters.
- Current-version transitions.
- Current-version expiration.
- Noncurrent-version transitions and expiration.
- Expired delete-marker cleanup.
- Incomplete multipart-upload cleanup.
- Potential conflicts between retention requirements and deletion actions.

Do not replace a working lifecycle configuration with a partial configuration that silently removes unrelated rules.

### Apply the reviewed configuration

After merging the intended policy changes into the complete lifecycle configuration:

```bash
aws s3api put-bucket-lifecycle-configuration \
  --bucket "$BUCKET" \
  --lifecycle-configuration file://lifecycle.json
```

This operation replaces the bucket's lifecycle configuration. Preserve and review existing rules before applying it.

Verify the deployed configuration:

```bash
aws s3api get-bucket-lifecycle-configuration \
  --bucket "$BUCKET"
```

For infrastructure-managed environments, use a reviewed Terraform, CloudFormation, or CDK change rather than allowing multiple unrelated deployment processes to overwrite the same configuration.

### Remember that lifecycle processing is asynchronous

Lifecycle actions are not synchronous deletion commands. S3 processes eligible objects according to its lifecycle system, so an object may remain visible in inventory or operational reports after reaching the configured age threshold.

Do not use the lifecycle age threshold as the sole enforcement mechanism for an immediate operational deletion requirement.

When immediate removal is required and permitted, use a controlled deletion workflow that handles the appropriate version IDs and validates the result.

## Audit Version and Lifecycle Behavior

### Inspect object versions

Use `list-object-versions` to inspect current versions, historical versions, and delete markers:

```bash
aws s3api list-object-versions \
  --bucket "$BUCKET" \
  --prefix "documents/customer-123/"
```

Review the `Versions` and `DeleteMarkers` collections separately. They contain different resource states and are both relevant to retention auditing.

For individual objects, inspect versions and select a specific `VersionId` only when performing a version-scoped operation.

### Check object metadata and version identifiers

```bash
aws s3api head-object \
  --bucket "$BUCKET" \
  --key "$OBJECT_KEY"
```

For a specific historical version:

```bash
aws s3api head-object \
  --bucket "$BUCKET" \
  --key "$OBJECT_KEY" \
  --version-id "$VERSION_ID"
```

These commands can help verify a version's accessibility and associated metadata. They do not by themselves prove that all retention or lifecycle requirements are satisfied.

### Use inventory and storage analytics for large buckets

Avoid repeatedly listing every version across a large production bucket for routine auditing.

Use S3 Inventory and S3 Storage Lens where appropriate to assess:
- Current and noncurrent version counts.
- Delete-marker counts.
- Total storage by version status and storage class where supported.
- Growth in historical object storage.
- Potential version proliferation caused by repeated overwrites.

For retention verification, compare the actual version population with the expected policy outcome. Historical versions can remain stored for valid reasons, including version retention rules, legal holds, and lifecycle processing that has not yet completed.

## Protect Retained Versions with Object Lock Where Required

S3 Object Lock provides retention controls for supported versioned general purpose buckets. It can protect object versions from permanent deletion during defined retention periods or legal holds.

Object Lock and Lifecycle should be designed together:
- Do not configure lifecycle deletion in a way that conflicts with mandatory retention obligations.
- Understand the difference between Governance and Compliance retention modes.
- Account for legal holds that can prevent deletion.
- Test retention configuration and recovery operations with representative objects.
- Treat retention changes as controlled security-sensitive operations.

A lifecycle rule does not override applicable Object Lock protections. A delete marker may be created for a protected version even though the protected version itself cannot be permanently deleted while its protections remain effective.

Reference: [Locking objects with S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).

## Avoid Common Versioning and Lifecycle Mistakes

| Mistake | Consequence | Better practice |
|---|---|---|
| Enabling versioning without noncurrent-version management | Historical versions can accumulate indefinitely | Define and verify an explicit retention policy |
| Assuming current-version expiration permanently deletes all data | Historical versions remain stored | Configure noncurrent-version expiration where permitted |
| Retaining a fixed number of versions without a time-based requirement | Rapid overwrites can shorten the effective recovery window | Base retention on business recovery requirements |
| Setting a noncurrent-version expiration period too aggressively | Useful recovery history is permanently deleted | Test the policy against realistic overwrite and recovery scenarios |
| Forgetting delete-marker cleanup | Unnecessary delete markers can accumulate | Add an eligible expired-delete-marker lifecycle rule |
| Using a tag filter for expired-delete-marker cleanup | The lifecycle rule is invalid for this action | Use a compatible prefix or other supported filter |
| Replacing the lifecycle configuration with a partial document | Existing retention or cleanup rules can disappear | Merge and review the full configuration before deployment |
| Assuming lifecycle actions occur immediately | Monitoring may incorrectly report a policy failure | Account for asynchronous lifecycle processing |
| Treating versioning as a backup strategy | A destructive action or lifecycle policy can affect recoverability | Maintain an appropriate backup and recovery design |
| Ignoring Object Lock and legal holds | Deletion may fail or violate retention requirements | Evaluate protection state and legal obligations before cleanup |

## Production Readiness Checklist

- [ ] Versioning is enabled for buckets that require historical recovery.
- [ ] The policy defines both recovery retention and business retention requirements.
- [ ] Current-version transitions are separate from noncurrent-version transitions where their access patterns differ.
- [ ] Noncurrent-version expiration is explicitly configured when permanent historical-data cleanup is required.
- [ ] `NewerNoncurrentVersions` is used only when version-count retention is an intentional requirement.
- [ ] Expired delete-marker cleanup is configured where appropriate.
- [ ] Lifecycle configuration changes preserve existing rules.
- [ ] Storage-class transition constraints, retrieval costs, and minimum storage durations have been reviewed.
- [ ] Object Lock and legal-hold requirements are respected.
- [ ] Version counts and delete-marker counts are monitored.
- [ ] Recovery tests verify that retained versions can be restored and accessed.
- [ ] Lifecycle execution is treated as asynchronous.
- [ ] Destructive policy changes are reviewed and validated before production rollout.

## Key Takeaways

- S3 Versioning preserves historical versions, while Lifecycle controls transitions, expiration, and cleanup; neither capability replaces the other.
- Current-version expiration in a versioned bucket normally creates a delete marker, so permanent historical-data cleanup requires separate noncurrent-version expiration.
- Configure time-based retention according to recovery and business requirements, and use newer-version counts only when version-depth limits are intentional.
- Treat lifecycle policy changes as destructive infrastructure changes: preserve existing rules, respect Object Lock, and verify the deployed configuration.
- Monitor current versions, noncurrent versions, and delete markers, and test actual recovery rather than assuming that versioning alone provides a complete backup strategy.
