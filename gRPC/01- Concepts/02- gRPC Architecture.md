# gRPC Architecture

# Overview

A gRPC application consists of several components working together to allow two applications to communicate efficiently.

At a high level, the architecture looks like this:

```text
                  gRPC Architecture

                 +----------------+
                 |     Client     |
                 +----------------+
                         |
                         |
                Calls Remote Method
                         |
                         ▼
                +----------------+
                |  Client Stub   |
                | (Generated)    |
                +----------------+
                         |
               Serialize Request
                         |
                         ▼
                +----------------+
                | Protocol Buffer|
                +----------------+
                         |
                    HTTP/2 Channel
                         |
                         ▼
                +----------------+
                |  Server Stub   |
                | (Generated)    |
                +----------------+
                         |
             Deserialize Request
                         |
                         ▼
                +----------------+
                | gRPC Service   |
                | Implementation |
                +----------------+
                         |
                  Business Logic
                         |
                         ▼
                +----------------+
                | Database / API |
                +----------------+
```

---

# Components of gRPC Architecture

The major components are:

1. Client
2. Channel
3. Client Stub
4. HTTP/2
5. Protocol Buffers
6. Server Stub
7. Service Implementation

Let's understand each one.

---

# 1. Client

The client is the application that wants to consume a service.

Instead of manually sending HTTP requests, the client simply calls a method generated by gRPC.

Example:

```python
response = employee_client.GetEmployee(request)
```

To the developer, this looks like a normal Python function call.

The client does not need to know:

- Network communication
- Serialization
- Socket programming
- HTTP details

gRPC handles all of these automatically.

---

# 2. Channel

A **Channel** represents the connection between the client and the server.

It is responsible for:

- Establishing the connection
- Sending requests
- Receiving responses
- Managing connection state
- Handling retries (when configured)
- Load balancing (when supported)

Example:

```python
channel = grpc.insecure_channel("localhost:50051")
```

or

```python
channel = grpc.secure_channel(...)
```

Channels are designed to be reused.

Creating a new channel for every request is considered a bad practice because establishing connections is expensive.

---

# 3. Client Stub

The client stub is automatically generated from the `.proto` file.

It acts as a local proxy for the remote service.

Example:

```python
stub = EmployeeServiceStub(channel)
```

When the application executes:

```python
stub.GetEmployee(request)
```

the stub automatically:

- Serializes the request
- Sends it over HTTP/2
- Waits for the response
- Deserializes the response
- Returns the final object

The developer never writes networking code.

---

# 4. Protocol Buffers

Protocol Buffers (Protobuf) define:

- Messages
- Services
- RPC methods

Example:

```proto
service EmployeeService {
    rpc GetEmployee(EmployeeRequest)
        returns (EmployeeResponse);
}
```

The `.proto` file is the contract between the client and server.

Both sides generate code from the same definition, ensuring consistency.

---

# 5. HTTP/2

Unlike traditional REST APIs, gRPC uses HTTP/2 as its transport protocol.

HTTP/2 provides several advantages:

- Binary communication
- Multiplexing
- Header compression
- Long-lived connections
- Streaming support
- Lower latency

These features make gRPC much faster than HTTP/1.1 for service-to-service communication.

---

# 6. Server Stub

Just as the client has a generated stub, the server also has one.

The server stub is responsible for:

- Receiving incoming requests
- Deserializing Protocol Buffer messages
- Invoking the correct service method
- Serializing the response
- Sending the response back to the client

The server implementation only focuses on business logic.

---

# 7. Service Implementation

This is where the application's business logic lives.

Example:

```python
class EmployeeService(EmployeeServiceServicer):

    def GetEmployee(self, request, context):
        # Business logic
        return EmployeeResponse(...)
```

Typical tasks include:

- Reading from a database
- Calling another microservice
- Performing calculations
- Accessing a cache
- Validating input

The service implementation does not deal with serialization or network communication.

# Request Flow

The following diagram illustrates how a gRPC request is processed.

```text
Client
   │
   │ 1. Calls RPC Method
   ▼
Client Stub
   │
   │ 2. Serialize Request
   ▼
Protocol Buffers
   │
   │ 3. Send via HTTP/2
   ▼
Network
   │
   ▼
Server Stub
   │
   │ 4. Deserialize Request
   ▼
Service Implementation
   │
   │ 5. Execute Business Logic
   ▼
Database / Cache / API
   │
   │ 6. Generate Response
   ▼
Server Stub
   │
   │ 7. Serialize Response
   ▼
HTTP/2
   │
   ▼
Client Stub
   │
   │ 8. Deserialize Response
   ▼
Client
```

# Why Use Generated Code?

Without generated code, developers would need to:

- Open network connections
- Serialize data manually
- Parse incoming responses
- Handle errors
- Maintain protocol compatibility

gRPC generates this code automatically from the `.proto` file.

Benefits include:

- Less boilerplate code
- Type safety
- Consistent APIs
- Better developer productivity
- Fewer serialization bugs

---

# Architecture Summary

| Component | Responsibility |
|-----------|----------------|
| Client | Initiates RPC calls |
| Channel | Maintains client-server connection |
| Client Stub | Acts as a local proxy and handles requests |
| Protocol Buffers | Defines messages and services |
| HTTP/2 | Efficient transport protocol |
| Server Stub | Receives requests and invokes service methods |
| Service Implementation | Contains application business logic |

---

# Key Takeaways

- gRPC follows a client-server architecture.
- Communication happens through generated client and server stubs.
- Protocol Buffers define the API contract.
- HTTP/2 provides fast and efficient transport.
- Channels manage long-lived connections between clients and servers.
- The service implementation focuses only on business logic, while gRPC handles networking and serialization.
