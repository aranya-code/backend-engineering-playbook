# 12- CLI Querying and Filtering

## Overview

CLI querying is the practical skill of using a database client to retrieve, filter, sort, aggregate, and inspect data efficiently from the terminal.

For PostgreSQL, the primary client is `psql`. The SQL itself is executed by PostgreSQL; `psql` mainly provides the interactive interface, formatting, scripting, variables, and client-side commands.

A backend engineer should be comfortable moving between:

```text
Interactive investigation
        ↓
SQL filtering
        ↓
Sorting / pagination
        ↓
Aggregation
        ↓
Query diagnostics
        ↓
Production-safe investigation
```

CLI querying is especially useful for:

- Debugging production issues
- Verifying application behavior
- Investigating unexpected records
- Validating migrations
- Checking data quality
- Inspecting operational state
- Reproducing ORM-generated SQL
- Running controlled administrative queries
- Building CI/CD and operational scripts

The key distinction is between **SQL executed by PostgreSQL** and **client-side commands executed by `psql`**.

---

## SQL vs `psql` Commands

`psql` supports both SQL and client-side meta-commands.

| Operation | Type | Example |
|---|---|---|
| Filter rows | SQL | `SELECT ... WHERE ...` |
| Sort results | SQL | `ORDER BY` |
| Aggregate | SQL | `GROUP BY` |
| Explain query | SQL | `EXPLAIN ...` |
| Show tables | `psql` command | `\dt` |
| Connect database | `psql` command | `\c appdb` |
| Show connection | `psql` command | `\conninfo` |
| Output formatting | `psql` command | `\x`, `\pset` |
| Execute SQL file | `psql` command | `\i script.sql` |

A useful mental model is:

```text
psql
 ├── Client commands
 │    ├── \dt
 │    ├── \d
 │    ├── \x
 │    └── \timing
 │
 └── SQL
      ├── SELECT
      ├── INSERT
      ├── UPDATE
      ├── DELETE
      └── EXPLAIN
             ↓
        PostgreSQL Server
```

## Establish a Safe Querying Context

Before querying an unfamiliar or production database:

```text
\conninfo
```

Then:

```sql
SELECT
    current_database(),
    current_user,
    inet_server_addr(),
    inet_server_port(),
    pg_is_in_recovery();
```

This verifies:

- Database
- User
- Server
- Port
- Primary/standby state

For production work, this should become habitual.

---

## Basic `SELECT`

A basic query:

```sql
SELECT
    id,
    email,
    created_at
FROM app.customers;
```

Prefer explicit columns over:

```sql
SELECT *
FROM app.customers;
```

Explicit projections reduce:

- Network transfer
- Application memory usage
- Serialization cost
- Accidental exposure of sensitive columns
- Coupling to schema changes

This matters even during CLI investigation because a large table may contain millions of rows.

---

## Filtering with `WHERE`

Filter records:

```sql
SELECT
    id,
    email,
    status
FROM app.customers
WHERE status = 'active';
```

Multiple conditions:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE status = 'active'
  AND created_at >= TIMESTAMPTZ '2026-01-01 00:00:00+00';
```

Use parentheses when boolean logic becomes complex:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE status = 'active'
  AND (
      plan = 'pro'
      OR plan = 'enterprise'
  );
```

## Comparison Operators

Common operators:

| Operator | Meaning |
|---|---|
| `=` | Equal |
| `<>` | Not equal |
| `>` | Greater than |
| `<` | Less than |
| `>=` | Greater than or equal |
| `<=` | Less than or equal |
| `IS NULL` | Null value |
| `IS NOT NULL` | Non-null value |
| `IN` | Membership |
| `BETWEEN` | Inclusive range |
| `LIKE` | Pattern matching |
| `ILIKE` | Case-insensitive pattern matching in PostgreSQL |

Example:

```sql
SELECT
    id,
    amount
FROM app.orders
WHERE amount >= 100
  AND amount < 500;
```

---

## `NULL` Filtering

`NULL` represents an unknown or missing value.

Do not write:

```sql
WHERE deleted_at = NULL
```

Use:

```sql
WHERE deleted_at IS NULL
```

or:

```sql
WHERE deleted_at IS NOT NULL
```

This is a common source of incorrect diagnostic queries.

SQL uses three-valued logic:

```text
TRUE
FALSE
UNKNOWN
```

Comparisons involving `NULL` generally evaluate to `UNKNOWN`, not `TRUE`.

---

## Filtering with `IN`

For multiple values:

```sql
SELECT
    id,
    status
FROM app.orders
WHERE status IN ('pending', 'processing', 'failed');
```

This is often clearer than:

```sql
WHERE status = 'pending'
   OR status = 'processing'
   OR status = 'failed'
```

For a large dynamic list generated by application code, parameterization is preferable to constructing SQL strings manually.

---

## Filtering with `BETWEEN`

Example:

```sql
SELECT
    id,
    total_amount
FROM app.orders
WHERE total_amount BETWEEN 100 AND 500;
```

`BETWEEN` is inclusive at both ends.

For timestamp ranges, half-open intervals are often safer:

```sql
SELECT
    id,
    created_at
FROM app.orders
WHERE created_at >= TIMESTAMPTZ '2026-09-01 00:00:00+00'
  AND created_at < TIMESTAMPTZ '2026-09-02 00:00:00+00';
```

This avoids ambiguity around fractional seconds and makes adjacent time windows composable.

---

## Pattern Matching

PostgreSQL:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE email ILIKE '%@example.com';
```

The leading wildcard can make ordinary B-tree indexes ineffective for this access pattern.

For production-scale search, evaluate:

```text
Prefix indexes
Expression indexes
pg_trgm
Full-text search
Dedicated search systems
```

Do not assume every `LIKE` or `ILIKE` query can efficiently use an index.

---

## Sorting with `ORDER BY`

```sql
SELECT
    id,
    created_at,
    total_amount
FROM app.orders
ORDER BY created_at DESC;
```

Multiple columns:

```sql
SELECT
    id,
    status,
    created_at
FROM app.orders
ORDER BY
    status ASC,
    created_at DESC;
```

For deterministic ordering, include a unique tie-breaker when necessary:

```sql
ORDER BY
    created_at DESC,
    id DESC;
```

This is especially important for pagination.

---

## Limiting Results

Use:

```sql
SELECT
    id,
    email
FROM app.customers
ORDER BY id
LIMIT 100;
```

This protects interactive sessions from accidentally dumping millions of rows into the terminal.

For production investigation, a bounded query is generally safer than an unrestricted query.

---

## Pagination with `OFFSET`

Example:

```sql
SELECT
    id,
    email
FROM app.customers
ORDER BY id
LIMIT 100
OFFSET 1000;
```

This is easy to understand but can become expensive for deep pages because PostgreSQL may still need to process or scan rows before the requested offset.

For large datasets, consider keyset pagination.

---

## Keyset Pagination

Example:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE id > 100000
ORDER BY id
LIMIT 100;
```

For descending timestamps with a unique identifier:

```sql
SELECT
    id,
    created_at,
    email
FROM app.customers
WHERE (created_at, id) < (
    TIMESTAMPTZ '2026-09-01 12:00:00+00',
    50000
)
ORDER BY
    created_at DESC,
    id DESC
LIMIT 100;
```

This pattern is generally more scalable for large result sets when supported by an appropriate index.

---

## Distinct Values

Use:

```sql
SELECT DISTINCT status
FROM app.orders
ORDER BY status;
```

For multiple columns:

```sql
SELECT DISTINCT
    customer_id,
    status
FROM app.orders;
```

`DISTINCT` may require sorting or hashing and can become expensive on large datasets.

Inspect the execution plan when performance matters.

---

## Counting Rows

Exact count:

```sql
SELECT COUNT(*)
FROM app.orders;
```

Filtered count:

```sql
SELECT COUNT(*)
FROM app.orders
WHERE status = 'completed';
```

For large tables, an exact count can require substantial work.

Do not repeatedly execute:

```sql
SELECT COUNT(*)
FROM huge_table;
```

as a lightweight monitoring mechanism.

For approximate operational metrics, use appropriate statistics or monitoring systems instead.

---

## Aggregation

Example:

```sql
SELECT
    status,
    COUNT(*) AS order_count
FROM app.orders
GROUP BY status
ORDER BY order_count DESC;
```

Multiple aggregates:

```sql
SELECT
    COUNT(*) AS order_count,
    SUM(total_amount) AS total_revenue,
    AVG(total_amount) AS average_order_value,
    MIN(total_amount) AS minimum_order_value,
    MAX(total_amount) AS maximum_order_value
FROM app.orders
WHERE created_at >= CURRENT_DATE - INTERVAL '7 days';
```

Aggregation is commonly used during production investigations to answer:

```text
How many?
How much?
How often?
Which category?
What changed?
```

---

## `HAVING`

`WHERE` filters rows before grouping.

`HAVING` filters groups after aggregation.

```sql
SELECT
    customer_id,
    COUNT(*) AS order_count
FROM app.orders
GROUP BY customer_id
HAVING COUNT(*) >= 10
ORDER BY order_count DESC;
```

Conceptually:

```text
FROM
 ↓
WHERE
 ↓
GROUP BY
 ↓
HAVING
 ↓
SELECT
 ↓
ORDER BY
 ↓
LIMIT
```

This is a logical processing model; PostgreSQL may physically execute operations differently after optimization.

---

## Querying with `JOIN`

Example:

```sql
SELECT
    o.id,
    o.created_at,
    c.email
FROM app.orders AS o
JOIN app.customers AS c
    ON c.id = o.customer_id
WHERE o.status = 'completed'
ORDER BY o.created_at DESC
LIMIT 100;
```

Use explicit join conditions.

Avoid accidental Cartesian products:

```sql
FROM orders, customers
```

unless a Cartesian product is intentionally required.

---

## `LEFT JOIN` for Missing Relationships

Find customers without orders:

```sql
SELECT
    c.id,
    c.email
FROM app.customers AS c
LEFT JOIN app.orders AS o
    ON o.customer_id = c.id
WHERE o.id IS NULL;
```

This is useful for data-quality investigations.

---

## Filtering on Joined Tables

Example:

```sql
SELECT
    o.id,
    c.email
FROM app.orders AS o
JOIN app.customers AS c
    ON c.id = o.customer_id
WHERE c.status = 'active'
  AND o.status = 'pending';
```

The optimizer may push predicates through the execution plan when semantically valid.

Do not assume the textual order of clauses determines physical execution.

---

## Subqueries

Example:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE id IN (
    SELECT customer_id
    FROM app.orders
    WHERE status = 'pending'
);
```

For existence checks, `EXISTS` is often clearer:

```sql
SELECT
    c.id,
    c.email
FROM app.customers AS c
WHERE EXISTS (
    SELECT 1
    FROM app.orders AS o
    WHERE o.customer_id = c.id
      AND o.status = 'pending'
);
```

The optimizer may transform these structures, so performance should be validated with `EXPLAIN`.

---

## Common Table Expressions

CTEs improve readability for multi-stage queries.

```sql
WITH recent_orders AS (
    SELECT
        id,
        customer_id,
        total_amount
    FROM app.orders
    WHERE created_at >= CURRENT_DATE - INTERVAL '7 days'
)
SELECT
    customer_id,
    COUNT(*) AS order_count,
    SUM(total_amount) AS revenue
FROM recent_orders
GROUP BY customer_id
ORDER BY revenue DESC;
```

CTEs are a query-structuring mechanism, not automatically a performance optimization.

PostgreSQL's treatment of CTEs depends on the query and version, and explicit `MATERIALIZED` or `NOT MATERIALIZED` can affect planning behavior.

## Querying JSONB

PostgreSQL JSONB fields can be queried directly.

Example:

```sql
SELECT
    id,
    metadata->>'source' AS source
FROM app.orders
WHERE metadata->>'source' = 'mobile';
```

Containment:

```sql
SELECT
    id
FROM app.orders
WHERE metadata @> '{"priority": "high"}';
```

For frequent JSONB access patterns, consider appropriate GIN or expression indexes.

Do not assume JSONB eliminates the need for relational schema design.

---

## Querying Arrays

Example:

```sql
SELECT
    id,
    tags
FROM app.products
WHERE 'backend' = ANY(tags);
```

For array-heavy access patterns, PostgreSQL supports specialized indexing approaches.

As with JSONB, validate actual query patterns before choosing an index strategy.

---

## Date and Time Filtering

Use explicit timestamp boundaries:

```sql
SELECT
    id,
    created_at
FROM app.orders
WHERE created_at >= TIMESTAMPTZ '2026-09-01 00:00:00+00'
  AND created_at < TIMESTAMPTZ '2026-09-02 00:00:00+00';
```

Avoid wrapping indexed timestamp columns in functions unnecessarily:

```sql
WHERE DATE(created_at) = DATE '2026-09-01'
```

A range predicate is usually more index-friendly:

```sql
WHERE created_at >= TIMESTAMPTZ '2026-09-01 00:00:00+00'
  AND created_at < TIMESTAMPTZ '2026-09-02 00:00:00+00'
```

This is an important example of **sargable** filtering.

---

## Sargability

A predicate is generally sargable when the database can efficiently use an index to find qualifying rows.

Prefer:

```sql
WHERE created_at >= TIMESTAMPTZ '2026-09-01 00:00:00+00'
```

over:

```sql
WHERE DATE(created_at) = DATE '2026-09-01'
```

Similarly, avoid unnecessary transformations on indexed columns.

If the transformation is required, an expression index may be appropriate:

```sql
CREATE INDEX customers_lower_email_idx
ON app.customers (lower(email));
```

Then:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE lower(email) = 'user@example.com';
```

## Querying Through `psql` From the Shell

Execute one query:

```bash
psql \
    -d appdb \
    -c "SELECT id, email FROM app.customers LIMIT 10;"
```

This is useful for:

```text
CI/CD
Operational scripts
Automation
One-off diagnostics
Shell pipelines
```

For scripts, consider:

```bash
psql \
    -d appdb \
    -v ON_ERROR_STOP=1 \
    -c "SELECT COUNT(*) FROM app.orders;"
```

`ON_ERROR_STOP` causes `psql` to stop on SQL errors instead of silently continuing through a script.

## Running a SQL File

Create:

```sql
SELECT
    status,
    COUNT(*)
FROM app.orders
GROUP BY status
ORDER BY status;
```

Execute:

```bash
psql \
    -d appdb \
    -f diagnostics.sql
```

Or inside `psql`:

```text
\i diagnostics.sql
```

For repeatable operational diagnostics, version-controlled SQL files are preferable to manually retyping complex queries.

## `psql` Variables

You can define variables:

```bash
psql \
    -d appdb \
    -v customer_id=123 \
    -c "SELECT id, email FROM app.customers WHERE id = :customer_id;"
```

For SQL scripts:

```sql
SELECT
    id,
    email
FROM app.customers
WHERE id = :customer_id;
```

`psql` variable substitution is a client-side feature.

It should not be confused with server-side parameter binding used by application drivers.

Be careful when substituting arbitrary text into SQL.

For application code, use parameterized queries through the database driver or ORM.

## Tuples Only

To suppress headers and formatting:

```text
\t
```

This is useful for shell scripts.

For example:

```bash
psql \
    -d appdb \
```

The `-A` option requests unaligned output and `-t` suppresses headers/footers.

## Querying Active Sessions

A production diagnostic query:

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    state,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

Use bounded output during incidents:

```sql
SELECT
    pid,
    usename,
    state,
    now() - query_start AS duration,
    wait_event_type,
    wait_event,
    left(query, 200) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start
LIMIT 50;
```

## Querying Locks

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    relation::regclass AS relation,
    waitstart
FROM pg_locks
ORDER BY granted, waitstart;
```

To find blocking relationships:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Do not treat every lock as an incident.

Locks are a normal part of transactional database operation.

The operational question is whether sessions are waiting unexpectedly and for how long.

## Query Diagnostics with `EXPLAIN`

Before optimizing:

```sql
EXPLAIN
SELECT
    id,
    email
FROM app.customers
WHERE email = 'user@example.com';
```

For actual execution:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    id,
    email
FROM app.customers
WHERE email = 'user@example.com';
```

`EXPLAIN ANALYZE` executes the query.

This is safe for `SELECT` in many diagnostic situations, but never assume it is harmless for arbitrary SQL.


## CLI Querying and ORMs

Django might generate SQL similar to:

```python
Customer.objects.filter(
    status="active"
).order_by("-created_at")[:100]
```

The production database still executes SQL.

Inspect generated SQL during development:

```python
queryset = (
    Customer.objects
    .filter(status="active")
    .order_by("-created_at")[:100]
)

print(queryset.query)
```

For deeper analysis, use Django's query logging, database instrumentation, and PostgreSQL `EXPLAIN`.

The CLI is therefore a useful boundary tool:

```text
Django ORM
    ↓
Generated SQL
    ↓
PostgreSQL
    ↓
Execution Plan
    ↓
Observed Runtime
```

## N+1 Query Investigation

An API may appear slow because it performs:

```text
1 query for customers
+
N queries for orders
```

The CLI can help reproduce individual queries and inspect their plans.

For example:

```sql
EXPLAIN (ANALYZE, BUFFERS)

    o.id,
    o.customer_id,
    o.created_at
```

But the database alone does not reveal the complete N+1 application pattern.

Combine:

```text
Application query logging
Request tracing
ORM inspection
Database statistics
EXPLAIN
```

## Querying Safely in Production

For diagnostic work, prefer:

```text
SELECT
LIMIT
Narrow projections
Specific predicates
Read-only transactions
Appropriate statement_timeout
```

For example:

```sql
BEGIN READ ONLY;

SET LOCAL statement_timeout = '5s';

SELECT
    id,
    status,
    created_at
FROM app.orders
WHERE customer_id = 123
ORDER BY created_at DESC
LIMIT 100;

COMMIT;
```

This does not make an expensive query automatically safe, but it provides useful operational boundaries.

---

## Statement Timeout

Set a session-level limit:

```sql
SET statement_timeout = '5s';
```

Or transaction-local:

```sql
BEGIN;

SET LOCAL statement_timeout = '5s';

SELECT
    ...
;

COMMIT;
```

This is useful for interactive diagnostics where an unexpectedly expensive query should not run indefinitely.

Understand the difference between:

```text
statement_timeout
lock_timeout
idle_in_transaction_session_timeout
```

They solve different problems.

---

## Read-Only Transactions

For investigations:

```sql
BEGIN READ ONLY;

SELECT ...
;

COMMIT;
```

This provides an additional guard against accidental writes within that transaction.

It does not prevent every possible side effect in every database feature, so it should complement—not replace—least privilege and careful operational access.

---

## Parameterized Queries

Never construct application SQL by concatenating untrusted values:

```text
SELECT ... WHERE email = 'user input'
```

Application code should use parameter binding.

For example with Python and psycopg:

```python
cursor.execute(
    """
    SELECT id, email
    FROM app.customers
    WHERE email = %s
    """,
    (email,),
)
```

The CLI is different because an engineer is usually manually constructing the query.

Nevertheless, when building scripts or automation, treat external input as untrusted and use appropriate parameterization or strict validation.

---

## Dynamic Identifiers

Values can be parameterized.

SQL identifiers generally cannot be passed as ordinary value parameters.

Unsafe conceptual pattern:

```text
SELECT * FROM <untrusted_table>
```

For dynamic administrative tooling, use an explicit allowlist of permitted identifiers or PostgreSQL's identifier-quoting facilities in the client library.

Do not assume that parameterization automatically makes arbitrary SQL structure safe.

---

## Performance Considerations

CLI querying can affect production just like application queries.

A query executed manually may consume:

```text
CPU
Memory
Disk I/O
Buffer cache
Locks
Connections
Network bandwidth
```

A query returning millions of rows can also overwhelm the engineer's terminal or local machine.

Before executing a large query:

```text
Estimate cardinality
Use LIMIT
Project only required columns
Check indexes
Use EXPLAIN
Set a timeout
Consider running against a replica
```

---

## Querying Read Replicas

For read-heavy diagnostics, a replica may reduce load on the primary.

However, remember:

```text
Primary
   ↓
Replication
   ↓
Replica
   ↓
Potential lag
```

A replica may not contain the latest committed state.

Use the primary when investigating questions that require current transactional state.

Use a replica when:

```text
Slight staleness is acceptable
The workload is read-heavy
The query is expensive
Replica capacity is available
```

```bash
    -d appdb \
    -v ON_ERROR_STOP=1 \
    -f verify_schema.sql
```

Good CI/CD SQL should be:

- Deterministic
- Idempotent where possible
- Bounded
- Observable
- Version-controlled
- Explicit about failure behavior

## Production Querying Checklist

Before running a diagnostic query:

| Question | Check |
|---|---|
| Target | Correct host and database? |
| Identity | Correct role? |
| Topology | Primary or replica? |
| Scope | How many rows might match? |
| Projection | Are all selected columns necessary? |
| Index | Is the predicate likely indexed? |
| Runtime | Could the query be expensive? |
| Timeout | Is an appropriate timeout configured? |
| Locking | Could the query interact with locks? |
| Network | Could the result be very large? |
| Security | Does the result contain sensitive data? |

## Common Mistakes

### Using `SELECT *`

It increases result size and exposes unnecessary data.

Prefer:

```sql
SELECT id, status, created_at
FROM app.orders
LIMIT 100;
```

### Forgetting `LIMIT`

An interactive query can accidentally dump millions of rows.

### Using `= NULL`

Use:

```sql
IS NULL
```

### Applying Functions to Indexed Columns

Prefer range predicates where possible.

### Assuming an Index Guarantees Fast Execution

PostgreSQL may choose a sequential scan when it estimates that it is cheaper.

### Using `EXPLAIN ANALYZE` Without Considering Side Effects

`EXPLAIN ANALYZE` executes the statement.

### Running Expensive Diagnostics on the Primary

Use an appropriate replica when consistency requirements allow it.

### Ignoring Result Transfer Cost

A fast database query can still create high end-to-end latency when returning a huge result set.

### Using Human-Formatted Output in Automation

Prefer machine-readable or stable output formats.

### Trusting `\timing` as a Benchmark

Interactive timing is useful for investigation but is not a controlled performance benchmark.

### Querying Without Verifying the Environment

The most dangerous CLI query is often the one executed against the wrong database.

## Practical Diagnostic Query Set

A compact PostgreSQL production investigation often starts with:

```sql
SELECT
    current_database(),
    current_user,
    inet_server_addr(),
    inet_server_port(),
    pg_is_in_recovery();
```

Then active sessions:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    now() - query_start AS duration,
    wait_event_type,
    wait_event,
    left(query, 300) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

Then blocking:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    left(query, 300) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Then query-level performance:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    id,
    status,
    created_at
FROM app.orders
WHERE customer_id = 123
ORDER BY created_at DESC
LIMIT 100;
```

This sequence moves from:

```text
Environment
    ↓
Runtime state
    ↓
Concurrency
    ↓
Query performance
```

without immediately changing database state.

## Key Takeaways

- **CLI querying is an operational skill:** use `psql` to investigate data, database state, performance, locks, and application behavior while distinguishing client commands from SQL executed by PostgreSQL.
- **Bound production queries deliberately:** project only required columns, use selective predicates and `LIMIT`, apply appropriate timeouts, and consider replicas when consistency requirements permit.
- **Understand query performance beyond syntax:** sargability, indexes, cardinality estimates, execution plans, result-transfer cost, locks, and concurrency all affect real latency.
- **Use CLI diagnostics with application observability:** correlate ORM-generated SQL, request traces, `pg_stat_activity`, `pg_stat_statements`, `EXPLAIN`, and database resource metrics rather than investigating queries in isolation.
- **Verify the target before every production investigation:** database, role, server, and primary/replica state should be confirmed before executing any query that could create significant load or expose sensitive data.
