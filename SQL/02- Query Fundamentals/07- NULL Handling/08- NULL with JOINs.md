# 08- NULL with JOINs

## Overview

`NULL` significantly affects SQL `JOIN` behavior because normal equality does not consider two `NULL` values equal.

The most important rule is:

```sql
NULL = NULL
```

does not evaluate to `TRUE`; it evaluates to `UNKNOWN`.

As a result, joining nullable columns requires deliberate handling. This matters in production systems where relationships may be optional, data may be incomplete, and outer joins are used to preserve entities that have no related records.

Understanding `NULL` with joins requires reasoning about:

- `INNER JOIN` versus outer joins.
- `NULL` values generated by unmatched outer-join rows.
- Nullable join keys.
- `ON` versus `WHERE` predicates.
- `IS NULL` and `IS NOT NULL`.
- `COALESCE()` and null-safe comparison.
- Join cardinality and duplicate rows.
- Query plans and index usage.

## NULL in JOIN Conditions

Consider two tables:

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    email TEXT
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    customer_id BIGINT,
    amount NUMERIC(12, 2)
);
```

A normal relationship is joined with:

```sql
SELECT
    c.id,
    c.email,
    o.id AS order_id,
    o.amount
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.id;
```

The equality condition works when both sides contain actual values.

If the join expression involves `NULL`:

```sql
NULL = 123
```

the result is `UNKNOWN`, so the row does not satisfy the join condition.

More importantly:

```sql
NULL = NULL
```

also evaluates to `UNKNOWN`.

Therefore, two rows with `NULL` join keys do **not** match under ordinary equality.

## INNER JOIN and NULL

An `INNER JOIN` returns only rows for which the join condition evaluates to `TRUE`.

Consider:

| `customers.id` | `orders.customer_id` |
|---:|---:|
| 1 | 1 |
| 2 | `NULL` |
| `3` | 3 |
| `NULL` | `NULL` |

A condition such as:

```sql
ON customers.id = orders.customer_id
```

matches:

```text
1 = 1
3 = 3
```

but not:

```text
NULL = NULL
```

because the latter is `UNKNOWN`.

### Practical implication

A nullable foreign-key-like column can silently prevent rows from joining.

For example:

```sql
SELECT
    c.id,
    o.id
FROM customers AS c
INNER JOIN orders AS o
    ON o.customer_id = c.id;
```

Orders where:

```text
customer_id IS NULL
```

are excluded.

This may be correct if an order is allowed to exist without a customer. If those orders should be visible, an `INNER JOIN` is the wrong relationship semantics.

## LEFT JOIN and Generated NULLs

A `LEFT JOIN` preserves every row from the left table.

```sql
SELECT
    c.id,
    c.email,
    o.id AS order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id;
```

For a customer with no matching order, SQL produces a result row where the columns from `orders` are `NULL`.

Conceptually:

```text
customers                 orders
---------                 ------
id = 1      ────────────> id = 101
id = 2      ────────────> no match
```

The result becomes:

| customer | order |
|---:|---:|
| 1 | 101 |
| 2 | `NULL` |

The `NULL` in the result does not necessarily mean the stored `orders.id` is actually `NULL`. It represents the absence of a matching right-side row.

This distinction is critical when interpreting query results.

## Identifying Rows With No Match

A common production query is:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.id IS NULL;
```

This identifies customers without orders.

The logic is:

1. Preserve all customers with `LEFT JOIN`.
2. Matching customers receive an `orders.id`.
3. Customers without a matching order receive `NULL`.
4. `WHERE o.id IS NULL` selects those unmatched rows.

This pattern is commonly called an **anti-join**.

## Anti-Join Alternatives

The same business question can often be expressed using `NOT EXISTS`:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);
```

For many production queries, `NOT EXISTS` is an excellent choice because it directly expresses:

> Return customers for which no matching order exists.

PostgreSQL can optimize both forms effectively depending on the query and indexes.

A useful index is:

```sql
CREATE INDEX idx_orders_customer_id
    ON orders (customer_id);
```

Always verify the actual plan for large datasets:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);
```

## LEFT JOIN and WHERE: The Most Important Trap

Consider:

```sql
SELECT
    c.id,
    o.id AS order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.amount > 100;
```

At first glance, this appears to mean:

> Return customers and orders over 100.

But the `WHERE` condition eliminates rows where:

```text
o.amount IS NULL
```

including the `NULL` values generated by the unmatched side of the `LEFT JOIN`.

Therefore, the query effectively behaves like an inner join for that condition.

### Move the predicate into ON when preserving unmatched rows

If the requirement is:

> Return every customer, but only attach orders whose amount is greater than 100.

write:

```sql
SELECT
    c.id,
    o.id AS order_id,
    o.amount
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
   AND o.amount > 100;
```

Now customers without qualifying orders remain in the result.

The difference is semantic:

```sql
WHERE o.amount > 100
```

filters the final result.

```sql
ON o.amount > 100
```

controls which right-side rows are eligible to match.

## ON vs WHERE With NULL

| Requirement | Predicate location |
|---|---|
| Remove rows from the final result | `WHERE` |
| Control which rows participate in an outer join | `ON` |
| Find unmatched left-side rows | `LEFT JOIN ... WHERE right.id IS NULL` |
| Preserve left rows while filtering right-side matches | Predicate in `ON` |
| Filter an `INNER JOIN` | Usually equivalent in many cases, subject to query semantics |

For `INNER JOIN`, moving a predicate between `ON` and `WHERE` often produces the same logical result.

For outer joins, the distinction can fundamentally change the result set.

## Nullable Join Keys

Suppose:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    external_id TEXT
);

CREATE TABLE events (
    id BIGINT PRIMARY KEY,
    external_user_id TEXT
);
```

If both columns can be `NULL`:

```sql
SELECT *
FROM users AS u
JOIN events AS e
    ON u.external_id = e.external_user_id;
```

rows where both identifiers are `NULL` do not match.

This is usually desirable because:

```text
NULL
```

means the value is unknown or absent, not a shared identifier.

Treating every missing value as belonging to the same identity would create incorrect relationships.

## Null-Safe Equality

Some databases provide operators or constructs that explicitly treat two `NULL` values as equal.

PostgreSQL provides:

```sql
IS NOT DISTINCT FROM
```

For example:

```sql
SELECT *
FROM users AS u
JOIN events AS e
    ON u.external_id IS NOT DISTINCT FROM e.external_user_id;
```

This treats:

```text
10    vs 10     → TRUE
10    vs 20     → FALSE
10    vs NULL   → FALSE
NULL  vs NULL   → TRUE
```

The opposite operator is:

```sql
IS DISTINCT FROM
```

This is useful when `NULL` is intentionally part of the comparison semantics.

However, using null-safe equality in a join is not automatically a good design. If `NULL` means "unknown identifier", matching all `NULL` values may create a many-to-many relationship and produce unexpected row multiplication.

## COALESCE in JOIN Conditions

A tempting pattern is:

```sql
ON COALESCE(a.key, 0) = COALESCE(b.key, 0)
```

This makes `NULL` values compare as though they were `0`.

For example:

```text
NULL → 0
NULL → 0
```

and therefore they match.

This is usually dangerous unless the domain explicitly defines `NULL` and `0` as equivalent.

It can also affect index usage because applying functions to indexed columns may prevent a straightforward index access path.

Prefer explicit semantics:

```sql
ON a.key = b.key
```

when NULLs should not match, or:

```sql
ON a.key IS NOT DISTINCT FROM b.key
```

when NULL-to-NULL matching is intentionally required.

## NULL With Composite JOIN Conditions

Join conditions frequently contain multiple predicates:

```sql
SELECT *
FROM orders AS o
JOIN shipments AS s
    ON s.order_id = o.id
   AND s.carrier = o.preferred_carrier;
```

If:

```text
o.preferred_carrier = NULL
```

then:

```sql
s.carrier = o.preferred_carrier
```

evaluates to `UNKNOWN`.

The entire `AND` condition therefore cannot become `TRUE` through that comparison.

If the business rule says a missing carrier should match another missing carrier, the query needs explicit null-safe semantics.

For PostgreSQL:

```sql
SELECT *
FROM orders AS o
JOIN shipments AS s
    ON s.order_id = o.id
   AND s.carrier IS NOT DISTINCT FROM o.preferred_carrier;
```

The important engineering principle is to define the meaning of a missing value before modifying the join condition.

## OR Conditions and NULL

Consider:

```sql
ON a.customer_id = b.customer_id
OR a.customer_id IS NULL
```

This does not mean:

> Match when customer IDs are equal, otherwise match NULLs safely.

It means:

> Match every row from `b` whenever `a.customer_id` is NULL.

That can create many matches.

For example, if one row has:

```text
a.customer_id = NULL
```

and `b` contains 1,000 rows, the condition may match all 1,000 rows.

This can cause:

- unexpected result multiplication;
- incorrect aggregates;
- large intermediate result sets;
- high CPU and memory consumption.

Never introduce `OR ... IS NULL` into a join condition without analyzing its cardinality.

## JOINs and Aggregates

Join multiplication becomes particularly dangerous when combined with aggregates.

Suppose:

```sql
customers
---------
id

orders
------
id
customer_id
amount

payments
--------
id
customer_id
amount
```

This query may be incorrect:

```sql
SELECT
    c.id,
    SUM(o.amount) AS order_total,
    SUM(p.amount) AS payment_total
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
LEFT JOIN payments AS p
    ON p.customer_id = c.id
GROUP BY c.id;
```

If a customer has:

```text
2 orders
3 payments
```

the joins can produce:

```text
2 × 3 = 6 rows
```

and both aggregates may be multiplied.

`NULL` makes this harder to reason about because customers with no orders or payments still produce outer-join rows.

### Safer approach

Aggregate each child relationship before joining:

```sql
WITH order_totals AS (
    SELECT
        customer_id,
        SUM(amount) AS order_total
    FROM orders
    GROUP BY customer_id
),
payment_totals AS (
    SELECT
        customer_id,
        SUM(amount) AS payment_total
    FROM payments
    GROUP BY customer_id
)
SELECT
    c.id,
    COALESCE(ot.order_total, 0) AS order_total,
    COALESCE(pt.payment_total, 0) AS payment_total
FROM customers AS c
LEFT JOIN order_totals AS ot
    ON ot.customer_id = c.id
LEFT JOIN payment_totals AS pt
    ON pt.customer_id = c.id;
```

This keeps each relationship at one row per customer before combining them.

The general rule is:

> Control join cardinality before performing aggregates.

## LEFT JOIN With COUNT

Consider:

```sql
SELECT
    c.id,
    COUNT(*) AS order_count
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
GROUP BY c.id;
```

This is incorrect for customers with no orders.

A `LEFT JOIN` still produces one result row for the customer, so:

```text
COUNT(*) = 1
```

Instead:

```sql
SELECT
    c.id,
    COUNT(o.id) AS order_count
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
GROUP BY c.id;
```

For a customer with no orders:

```text
o.id = NULL
COUNT(o.id) = 0
```

This is one of the most common SQL interview traps involving `NULL`.

## NULL and Foreign Keys

In a relational schema, a nullable foreign key commonly represents an optional relationship.

For example:

```sql
CREATE TABLE tickets (
    id BIGINT PRIMARY KEY,
    assigned_user_id BIGINT REFERENCES users(id)
);
```

A ticket with:

```text
assigned_user_id = NULL
```

can represent:

> This ticket is currently unassigned.

Then:

```sql
SELECT
    t.id,
    u.id AS assigned_user_id
FROM tickets AS t
LEFT JOIN users AS u
    ON u.id = t.assigned_user_id;
```

is appropriate because unassigned tickets should remain visible.

You can identify them directly:

```sql
SELECT
    id
FROM tickets
WHERE assigned_user_id IS NULL;
```

The database constraint and application semantics should agree about what `NULL` means.

## NULL With Multiple JOINs

Consider an API query:

```sql
SELECT
    o.id,
    c.email,
    a.city,
    s.tracking_number
FROM orders AS o
LEFT JOIN customers AS c
    ON c.id = o.customer_id
LEFT JOIN addresses AS a
    ON a.id = o.shipping_address_id
LEFT JOIN shipments AS s
    ON s.order_id = o.id;
```

Each `LEFT JOIN` can introduce another set of nullable result columns.

An order might therefore produce:

```text
customer → present
address  → NULL
shipment → NULL
```

The application must distinguish:

- an actual nullable column;
- a missing related row;
- an unknown value;
- a relationship that does not exist.

This is especially important when mapping SQL results into Django models, FastAPI/Pydantic response models, or gRPC response messages.

## JOIN Behavior Reference

| Join type | Unmatched left row | Unmatched right row | NULL generated? |
|---|---|---|---|
| `INNER JOIN` | Removed | Removed | No |
| `LEFT JOIN` | Preserved | N/A | Right-side columns |
| `RIGHT JOIN` | N/A | Preserved | Left-side columns |
| `FULL OUTER JOIN` | Preserved | Preserved | Columns from missing side |

For most backend application queries, `LEFT JOIN` and `INNER JOIN` are substantially more common than `RIGHT JOIN` or `FULL OUTER JOIN`.

## Production Performance Considerations

`NULL` itself is rarely the primary performance problem. The larger concerns are usually:

- nullable join keys;
- low-selectivity predicates;
- functions applied to join columns;
- incorrect join cardinality;
- accidental many-to-many matches;
- missing indexes;
- filtering after large outer joins.

For a common foreign-key relationship:

```sql
CREATE INDEX idx_orders_customer_id
    ON orders (customer_id);
```

can support joins such as:

```sql
SELECT
    c.id,
    o.id
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.id;
```

If the query also filters:

```sql
WHERE o.status = 'pending'
```

the optimal index may depend on table size, data distribution, query frequency, and the database optimizer.

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
```

rather than assuming an index is being used effectively.

Avoid unnecessary expressions such as:

```sql
ON COALESCE(o.customer_id, 0) = c.id
```

when ordinary equality expresses the required semantics.

## Production Design Recommendations

### Prefer Non-Nullable Foreign Keys When the Relationship Is Mandatory

If every order must belong to a customer:

```sql
customer_id BIGINT NOT NULL REFERENCES customers(id)
```

is preferable to:

```sql
customer_id BIGINT REFERENCES customers(id)
```

This moves an invariant into the database and simplifies joins.

### Use NULL for Real Absence or Unknown State

Do not use `NULL` merely because the application does not want to decide what a value should be.

Define whether the field means:

- unknown;
- not applicable;
- not yet calculated;
- optional relationship;
- intentionally absent.

### Avoid NULL-Safe Matching Unless Required

If `NULL` represents an unknown identifier, matching:

```text
NULL ↔ NULL
```

is generally incorrect.

Use ordinary equality unless the domain explicitly requires null-safe equality.

### Test Outer-Join Queries With Missing Relationships

For every important `LEFT JOIN`, test at least:

- one matching child;
- multiple matching children;
- no matching child;
- nullable child attributes;
- duplicate or unexpected relationship data.

These cases expose most production bugs.

## Common Mistakes and Pitfalls

| Mistake | Problem | Correct approach |
|---|---|---|
| Expecting `NULL = NULL` to match | Equality with NULL produces `UNKNOWN` | Use `IS NOT DISTINCT FROM` only when NULL-to-NULL matching is intended |
| Using `WHERE right_table.column = ...` after a `LEFT JOIN` | Can eliminate unmatched rows | Move the predicate to `ON` when unmatched left rows must remain |
| Using `COUNT(*)` to count children after `LEFT JOIN` | Counts the preserved parent row | Use `COUNT(child.id)` |
| Replacing NULL with `0` using `COALESCE()` in a join | Can equate semantically different values | Define domain semantics first |
| Adding `OR column IS NULL` carelessly | Can create many-to-many matches | Analyze join cardinality explicitly |
| Assuming outer-join NULL means stored NULL | It may represent no related row | Distinguish missing rows from nullable stored values |
| Joining multiple one-to-many relationships before aggregation | Multiplies rows and inflates totals | Pre-aggregate each relationship |
| Applying functions to join keys | May prevent efficient index access | Prefer direct indexed comparisons when possible |
| Making every foreign key nullable | Weakens data integrity and complicates queries | Use `NOT NULL` for mandatory relationships |
| Ignoring NULL test cases | Queries work only with complete data | Test missing relationships explicitly |

## Interview Traps

### Does `NULL = NULL` return TRUE?

No.

It returns:

```text
UNKNOWN
```

because `NULL` represents an unknown or absent value.

### Why does this return customers without orders?

```sql
SELECT c.id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.id IS NULL;
```

The `LEFT JOIN` preserves every customer. Customers without matching orders receive a generated `NULL` for `o.id`, which the `WHERE` clause selects.

### Why can this turn a LEFT JOIN into an effective INNER JOIN?

```sql
SELECT *
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.status = 'completed';
```

Unmatched customers have:

```text
o.status = NULL
```

and:

```text
NULL = 'completed'
```

is `UNKNOWN`, so those rows are removed.

### How do you preserve customers while filtering their orders?

Put the filter in the join condition:

```sql
SELECT *
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
   AND o.status = 'completed';
```

### Should two NULL foreign keys match?

Usually no.

If `NULL` means an unknown or absent relationship, matching two NULLs would create a relationship that does not actually exist.

### What is the PostgreSQL null-safe equality operator?

PostgreSQL provides:

```sql
IS NOT DISTINCT FROM
```

which considers two `NULL` values equal for comparison purposes.

### Why is `COALESCE()` in a JOIN potentially dangerous?

This:

```sql
ON COALESCE(a.key, 0) = COALESCE(b.key, 0)
```

changes the domain semantics by making `NULL` equivalent to `0`. It can also complicate index usage and create unexpected matches.

### Why can multiple LEFT JOINs inflate aggregates?

Joining two independent one-to-many relationships can multiply rows.

For example:

```text
2 orders × 3 payments = 6 joined rows
```

Aggregating after that multiplication can overstate totals.

## Key Takeaways

- **Ordinary join equality does not match NULL values; `NULL = NULL` evaluates to UNKNOWN, not TRUE.**
- **`LEFT JOIN` generates NULLs for missing right-side rows, making `WHERE right.id IS NULL` a useful anti-join pattern.**
- **For outer joins, predicates in `ON` and `WHERE` have different semantics; placing right-side filters in `WHERE` can eliminate unmatched rows.**
- **Do not use `COALESCE()` or `OR ... IS NULL` in joins without explicitly defining the intended NULL semantics and analyzing cardinality.**
- **Control join cardinality before aggregation, and prefer `NOT NULL` foreign keys when relationships are mandatory.**
