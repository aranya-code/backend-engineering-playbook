# 05- Filtering Exercises

## Overview

Filtering is one of the most fundamental SQL skills, but production filtering requires more than knowing `WHERE`.

A backend engineer must be able to reason about:

- Equality and range predicates.
- `NULL` and three-valued logic.
- Boolean conditions.
- Pattern matching.
- Date and timestamp boundaries.
- `IN`, `EXISTS`, and `NOT EXISTS`.
- Filtering before versus after aggregation.
- Join predicates and outer-join semantics.
- Index-friendly predicates.
- Tenant and authorization filters.
- Large datasets and pagination.
- Dynamic filters generated by Django, FastAPI, or SQLAlchemy.
- Query plans and production workload behavior.

These exercises use PostgreSQL and the schema below.

The goal is not merely to produce a query that returns the expected rows. For every exercise, understand **why the predicate is correct, how `NULL` affects it, whether it can use an index, and how it behaves when the dataset becomes large or concurrent**.

## Practice Schema

Use the following schema for the exercises.

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    name text NOT NULL,
    status text NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'inactive', 'suspended')),
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    name text NOT NULL,
    price numeric(12, 2) NOT NULL
        CHECK (price >= 0),
    active boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(id),
    status text NOT NULL
        CHECK (status IN ('pending', 'processing', 'completed', 'cancelled')),
    total_amount numeric(12, 2) NOT NULL
        CHECK (total_amount >= 0),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
    order_id bigint NOT NULL
        REFERENCES orders(id),
    product_id bigint NOT NULL
        REFERENCES products(id),
    quantity integer NOT NULL
        CHECK (quantity > 0),
    unit_price numeric(12, 2) NOT NULL
        CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
```

Useful indexes for filtering exercises:

```sql
CREATE INDEX orders_customer_created_idx
ON orders (customer_id, created_at DESC);

CREATE INDEX orders_status_created_idx
ON orders (status, created_at DESC);

CREATE INDEX products_active_price_idx
ON products (active, price);
```

Index usefulness should always be verified against the actual workload and execution plan.

## Filtering Fundamentals

### Equality Filtering

Find active customers:

```sql
SELECT
    id,
    email,
    name
FROM customers
WHERE status = 'active';
```

The predicate:

```sql
status = 'active'
```

selects rows whose `status` value is exactly `'active'`.

## Multiple Conditions

Use `AND` when all conditions must be true:

```sql
SELECT
    id,
    email,
    name
FROM customers
WHERE status = 'active'
  AND created_at >= $1;
```

Use `OR` when either condition may qualify:

```sql
SELECT
    id,
    email,
    name,
    status
FROM customers
WHERE status = 'suspended'
   OR status = 'inactive';
```

### Exercise

Find:

- Active customers created after a specified timestamp.
- Orders that are completed and worth more than a specified amount.
- Products that are active and cost more than `100`.
- Customers that are inactive or suspended.

---

## Operator Precedence

SQL boolean expressions require careful attention to precedence.

Consider:

```sql
WHERE status = 'active'
   OR status = 'suspended'
  AND created_at >= $1;
```

This is interpreted as:

```text
status = 'active'
OR
(status = 'suspended' AND created_at >= $1)
```

If the intended logic is:

```text
(active OR suspended)
AND recently created
```

write:

```sql
WHERE (status = 'active' OR status = 'suspended')
  AND created_at >= $1;
```

### Senior Rule

Use parentheses when they make business logic explicit, even when SQL precedence technically makes them unnecessary.

---

## IN Filtering

Instead of:

```sql
WHERE status = 'active'
   OR status = 'suspended'
```

use:

```sql
WHERE status IN ('active', 'suspended');
```

`IN` is particularly useful when a filter comes from a validated collection.

```sql
SELECT
    id,
    status,
    total_amount
FROM orders
WHERE status IN ('pending', 'processing');
```

### Exercise

Write queries using `IN` to find:

1. Customers with selected statuses.
2. Orders in several lifecycle states.
3. Products with selected IDs.

---

## NOT IN

Use `NOT IN` carefully:

```sql
SELECT
    id,
    status
FROM customers
WHERE status NOT IN ('inactive', 'suspended');
```

The major trap is `NULL`.

Consider:

```sql
WHERE customer_id NOT IN (
    SELECT customer_id
    FROM some_table
);
```

If the subquery contains `NULL`, SQL's three-valued logic can make the predicate evaluate to `UNKNOWN` rather than `TRUE`.

For anti-join logic, prefer:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM some_table AS s
    WHERE s.customer_id = c.id
);
```

when the semantics are "no matching row exists."

## NULL Filtering

`NULL` represents an unknown or missing value. It is not equal to zero, an empty string, or another `NULL`.

Incorrect:

```sql
WHERE some_column = NULL;
```

Correct:

```sql
WHERE some_column IS NULL;
```

And:

```sql
WHERE some_column IS NOT NULL;
```

## Three-Valued Logic

SQL predicates can evaluate to:

| Result | Meaning |
|---|---|
| `TRUE` | Row qualifies |
| `FALSE` | Row does not qualify |
| `UNKNOWN` | Usually caused by `NULL` |

For example:

```sql
NULL > 100
```

does not evaluate to `FALSE`; it evaluates to `UNKNOWN`.

A `WHERE` clause returns only rows for which the predicate evaluates to `TRUE`.

This matters when filtering nullable columns.

---

## Boolean Filtering

For a PostgreSQL boolean:

```sql
SELECT
    id,
    sku,
    name
FROM products
WHERE active = true;
```

PostgreSQL also allows:

```sql
WHERE active;
```

For false values:

```sql
WHERE NOT active;
```

Be careful if the column is nullable.

If `active` can be `NULL`, then:

```sql
WHERE NOT active
```

does not include `NULL`.

If the business meaning is:

> Anything other than active should be treated as inactive

the predicate must explicitly represent that rule.

---

## Range Filtering

Find expensive products:

```sql
SELECT
    id,
    sku,
    name,
    price
FROM products
WHERE price >= 100;
```

Find products within a range:

```sql
SELECT
    id,
    sku,
    name,
    price
FROM products
WHERE price >= 50
  AND price < 100;
```

For numeric ranges, half-open intervals are often easier to compose:

```text
[start, end)
```

rather than:

```text
[start, end]
```

---

## BETWEEN

This is valid:

```sql
WHERE price BETWEEN 50 AND 100;
```

`BETWEEN` is inclusive at both ends.

It is equivalent to:

```sql
WHERE price >= 50
  AND price <= 100;
```

For timestamps, inclusive upper boundaries can cause subtle bugs.

Prefer:

```sql
WHERE created_at >= $1
  AND created_at < $2;
```

for adjacent time windows.

---

## Date and Timestamp Filtering

Avoid converting an indexed timestamp column into a date unnecessarily:

```sql
WHERE created_at::date = $1;
```

This may prevent efficient use of a normal index on `created_at`.

Prefer a range:

```sql
WHERE created_at >= $1
  AND created_at < $2;
```

For example, to query one UTC day:

```text
2026-09-05 00:00:00 UTC
through
2026-09-06 00:00:00 UTC
```

use:

```sql
WHERE created_at >= '2026-09-05T00:00:00Z'
  AND created_at < '2026-09-06T00:00:00Z';
```

The application should establish the intended timezone before constructing these boundaries.

---

## Current-Time Filtering

Find orders created in the last 24 hours:

```sql
SELECT
    id,
    customer_id,
    status,
    created_at
FROM orders
WHERE created_at >= now() - interval '24 hours';
```

This is useful for operational queries, but production dashboards and scheduled jobs should have clearly defined timezone and boundary semantics.

## Pattern Matching

### Prefix Search

```sql
SELECT
    id,
    email,
    name
FROM customers
WHERE email LIKE 'alice%';
```

A prefix search can often use an appropriate B-tree index depending on collation/operator-class considerations.

### Suffix Search

```sql
WHERE email LIKE '%@example.com';
```

A normal B-tree index generally cannot efficiently satisfy an arbitrary leading-wildcard search.

For search-heavy workloads, consider:

- Trigram indexes.
- Full-text search.
- A dedicated search engine.

Do not add an index without first identifying the search pattern and workload.

---

## Case-Insensitive Filtering

PostgreSQL supports:

```sql
WHERE email ILIKE $1;
```

For example:

```sql
WHERE name ILIKE '%alice%';
```

A normal B-tree index may not efficiently support this arbitrary substring search.

For repeated substring searches, PostgreSQL's `pg_trgm` extension can be appropriate:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX customers_name_trgm_idx
ON customers
USING gin (name gin_trgm_ops);
```

Then:

```sql
SELECT
    id,
    name
FROM customers
WHERE name ILIKE '%alice%';
```

should be validated with `EXPLAIN`.

---

## NULL-Safe Comparison

PostgreSQL provides:

```sql
IS DISTINCT FROM
```

and:

```sql
IS NOT DISTINCT FROM
```

These operators treat `NULL` as a comparable value.

For example:

```sql
WHERE old_value IS DISTINCT FROM new_value;
```

can be useful when determining whether a value actually changed.

This is often safer than:

```sql
WHERE old_value <> new_value;
```

when either side can be `NULL`.

---

## Filtering With CASE

`CASE` can encode conditional logic.

```sql
SELECT
    id,
    total_amount,
    CASE
        WHEN total_amount >= 1000 THEN 'high'
        WHEN total_amount >= 500 THEN 'medium'
        ELSE 'standard'
    END AS order_class
FROM orders;
```

Filtering on a computed classification can be written as:

```sql
SELECT
    id,
    total_amount
FROM orders
WHERE CASE
    WHEN total_amount >= 1000 THEN 'high'
    WHEN total_amount >= 500 THEN 'medium'
    ELSE 'standard'
END = 'high';
```

However, this can be less efficient than expressing the predicate directly:

```sql
WHERE total_amount >= 1000;
```

Prefer direct predicates when the business condition can be expressed naturally.

---

## Filtering With COALESCE

Suppose a nullable value should be treated as a fallback:

```sql
WHERE COALESCE(last_login_at, created_at) >= $1;
```

This is semantically useful when the requirement is:

> Use `last_login_at` when available; otherwise use `created_at`.

But functions around columns can affect index usage.

If this becomes a high-frequency production query, evaluate:

- Query frequency.
- Existing indexes.
- Data distribution.
- Expression indexes.
- Alternative schema design.

---

## EXISTS Filtering

Find customers with at least one completed order:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
      AND o.status = 'completed'
);
```

`EXISTS` is ideal when the question is:

> Does at least one related row exist?

It avoids producing duplicate parent rows simply because multiple child rows match.

---

## NOT EXISTS Filtering

Find customers with no orders:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);
```

This is an important anti-join pattern.

## Filtering With JOIN

Find customers with completed orders:

```sql
SELECT DISTINCT
    c.id,
    c.email
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.status = 'completed';
```

This works, but `DISTINCT` may be unnecessary if the actual requirement is only existence.

Prefer:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
      AND o.status = 'completed'
);
```

when the business question is explicitly existence.

---

## Filtering LEFT JOIN Results

Suppose the requirement is:

> Return every customer, along with their completed orders if any exist.

Correct:

```sql
SELECT
    c.id,
    c.email,
    o.id AS order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
   AND o.status = 'completed';
```

A common mistake is:

```sql
SELECT
    c.id,
    c.email,
    o.id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.status = 'completed';
```

The `WHERE` condition removes rows where `o.status` is `NULL`, effectively turning the outer join into an inner-like result.

This distinction is a frequent SQL interview topic.

---

## Filtering Joined Data With Multiple Conditions

Find active customers with completed orders above `500`:

```sql
SELECT DISTINCT
    c.id,
    c.email
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.id
WHERE c.status = 'active'
  AND o.status = 'completed'
  AND o.total_amount > 500;
```

Before using `DISTINCT`, ask whether the requirement is actually:

```text
customer has at least one matching order
```

If so:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE c.status = 'active'
  AND EXISTS (
      SELECT 1
      FROM orders AS o
      WHERE o.customer_id = c.id
        AND o.status = 'completed'
        AND o.total_amount > 500
  );
```

is often a clearer expression of intent.

## Filtering Aggregated Results

`WHERE` filters rows before aggregation.

`HAVING` filters groups after aggregation.

Find customers whose completed order value exceeds `10,000`:

```sql
SELECT
    customer_id,
    SUM(total_amount) AS completed_value
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING SUM(total_amount) > 10000;
```

The logical flow is:

```text
FROM
 ↓
WHERE
 ↓
GROUP BY
 ↓
Aggregate
 ↓
HAVING
 ↓
SELECT
```

4. Customers whose average completed order exceeds `250`.

## Conditional Aggregation

Find customers with counts of different order states:

```sql
SELECT
    customer_id,
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (
        WHERE status = 'completed'
    ) AS completed_orders,
    COUNT(*) FILTER (
        WHERE status = 'cancelled'
    ) AS cancelled_orders
FROM orders
GROUP BY customer_id;
```

This is often cleaner than multiple correlated subqueries.

## Filtering With Window Functions

Window functions operate after the relevant input rows have been formed, but filtering directly on a window function generally requires another query level.

Find each customer's most recent order:

```sql
SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, id DESC
        ) AS row_number
    FROM orders AS o
) AS ranked
WHERE row_number = 1;
```

The `id` tie-breaker makes the ordering deterministic when timestamps are equal.

---

## Filtering Top-N Per Group

Find the three most recent orders for every customer:

```sql
SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, id DESC
        ) AS row_number
    FROM orders AS o
) AS ranked
WHERE row_number <= 3;
```

This is a common interview exercise because it combines:

- Partitioning.
- Ordering.
- Window functions.
- Outer filtering.

## Filtering JSONB

Suppose products contain metadata:

```sql
ALTER TABLE products
ADD COLUMN metadata jsonb;
```

Find products whose metadata contains a particular property:

```sql
SELECT
    id,
    sku,
    name
FROM products
WHERE metadata @> '{"category": "electronics"}';
```

For frequently queried JSONB structures, a GIN index may be appropriate:

```sql
CREATE INDEX products_metadata_gin_idx
ON products
USING gin (metadata);
```

JSONB should not automatically replace relational columns for heavily queried, constrained business attributes.

## Dynamic Filtering in Backend APIs

A REST endpoint might support:

```text
GET /orders?status=completed&min_amount=100&created_after=2026-09-01
```

The application should translate validated parameters into parameterized SQL.

Conceptually:

```text
HTTP parameters
      ↓
Validation
      ↓
Allowed filter fields
      ↓
Parameterized predicates
      ↓
SQL
      ↓
PostgreSQL
```

Never construct arbitrary SQL from request parameters.

Unsafe:

```python
query = f"""
    SELECT id, status
    FROM orders
    WHERE status = '{status}'
"""
```

Use parameter binding through the database driver or ORM.

## Django Filtering

Django's ORM can express filters safely:

```python
orders = (
    Order.objects
    .filter(
        status="completed",
        total_amount__gte=100,
    )
    .order_by("-created_at")
)
```

Multiple alternatives:

```python
from django.db.models import Q

orders = Order.objects.filter(
    Q(status="completed") | Q(status="processing")
)
```

For exclusion:

```python
orders = Order.objects.exclude(
    status="cancelled"
)
```

Senior-level concerns include:

- Generated SQL.
- Query count.
- Index alignment.
- Pagination.
- Join cardinality.
- Authorization.
- Tenant filtering.
- Query-plan stability.

ORM syntax should not hide database behavior.

## Django Filtering With Related Models

Find orders belonging to active customers:

```python
orders = (
    Order.objects
    .filter(
        customer__status="active",
        status="completed",
    )
)
```

For existence-style logic, Django also provides `Exists`.

```python
from django.db.models import Exists, OuterRef

completed_orders = Order.objects.filter(
    customer_id=OuterRef("pk"),
    status="completed",
)

customers = Customer.objects.annotate(
    has_completed_order=Exists(completed_orders)
).filter(
    has_completed_order=True
)
```

This can express database-side existence without loading related rows into Python.

## SQLAlchemy Filtering

A SQLAlchemy query can be built from validated application filters:

```python
from sqlalchemy import select

statement = (
    select(Order)
    .where(
        Order.status == "completed",
        Order.total_amount >= 100,
    )
    .order_by(Order.created_at.desc())
)
```

For dynamic filters, construct expressions only from known application fields.

Do not expose arbitrary SQL expressions through an API parameter.

## Filtering and Sargability

A predicate is generally easier for an index to support when the indexed column can be compared directly to a value or range.

Prefer:

```sql
WHERE created_at >= $1
```

over:

```sql
WHERE DATE(created_at) = $1;
```

Prefer:

```sql
WHERE price >= $1
```

over unnecessarily transforming:

```sql
WHERE price * 1.2 >= $1;
```

The exact optimizer behavior depends on the expression and available indexes, but the principle is:

> Avoid unnecessary transformations of indexed columns in frequently executed predicates.

If a transformed expression is genuinely required, consider an expression index.

---

## Filtering and Composite Indexes

Suppose the query is:

```sql
SELECT
    id,
    customer_id,
    status,
    created_at
FROM orders
WHERE customer_id = $1
  AND status = 'completed'
ORDER BY created_at DESC
LIMIT 50;
```

A possible index is:

```sql
CREATE INDEX orders_customer_status_created_idx
ON orders (
    customer_id,
    status,
    created_at DESC
);
```

The index follows the access pattern:

```text
customer_id equality
       ↓
status equality
       ↓
created_at ordering
       ↓
LIMIT
```

Index ordering should be driven by workload evidence, not a universal rule.

---

## Filtering Low-Cardinality Columns

A filter such as:

```sql
WHERE status = 'active'
```

may match a large percentage of the table.

An index is not automatically useful merely because the column appears in `WHERE`.

PostgreSQL may correctly choose a sequential scan when:

```text
Most rows qualify
+
Table pages are cheap to scan
```

This is why:

```text
WHERE clause
≠
automatic index scan
```

Always validate with `EXPLAIN`.

---

## Partial Indexes for Filtering

Suppose most queries operate only on active orders:

```sql
CREATE INDEX orders_active_created_idx
ON orders (created_at DESC)
WHERE status IN ('pending', 'processing');
```

This can reduce index size and write overhead compared with indexing every row.

It is especially useful when the predicate matches a stable, selective subset of the workload.

The query predicate must be compatible with the partial-index condition for the planner to use it.

---

## Filtering and Tenant Isolation

A multi-tenant query should normally include tenant scope:

```sql
SELECT
    id,
    status,
    total_amount
FROM orders
WHERE organization_id = $1
  AND status = 'completed'
ORDER BY created_at DESC
LIMIT 50;
```

Tenant filtering is not merely a performance concern.

It is an authorization boundary.

A missing tenant predicate can expose another customer's data.

For frequently accessed multi-tenant data, indexes often need to reflect tenant-scoped access patterns:

```sql
CREATE INDEX orders_org_status_created_idx
ON orders (
    organization_id,
    status,
    created_at DESC
);
```

If PostgreSQL Row-Level Security is used, application-level filtering and database-enforced policies must be designed together.

---

## Filtering and Pagination

Filtering and pagination should be designed together.

Bad:

```sql
SELECT *
FROM orders
WHERE status = 'completed'
ORDER BY created_at DESC
LIMIT 50
OFFSET 100000;
```

For large datasets, keyset pagination is often more scalable:

```sql
SELECT
    id,
    customer_id,
    status,
    total_amount,
    created_at
FROM orders
WHERE status = 'completed'
  AND (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

The tuple comparison provides a deterministic cursor.

A matching index can support the access pattern:

```sql
CREATE INDEX orders_completed_cursor_idx
ON orders (
    status,
    created_at DESC,
    id DESC
);
```

## Filtering and Execution Plans

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    id,
    customer_id,
    status
FROM orders
WHERE customer_id = $1
  AND status = 'completed';
```

Inspect:

- Scan type.
- Estimated rows.
- Actual rows.
- Planning time.
- Execution time.
- Buffer activity.
- Rows removed by filter.
- Join behavior if relationships are involved.

A sequential scan is not automatically a problem.

A missing index is not automatically the explanation for a slow query.

---

## Filtering and Cardinality Estimates

Suppose:

```sql
WHERE status = 'completed'
  AND customer_id = $1
```

The optimizer estimates how many rows satisfy the predicates.

If the estimates are badly wrong, PostgreSQL may choose a poor plan.

Possible causes include:

- Stale statistics.
- Correlated columns.
- Data skew.
- Rapidly changing distributions.
- Missing extended statistics.
- Incorrect assumptions about selectivity.

When filtering performance changes unexpectedly, investigate statistics as well as indexes.

---

## Filtering and Query Frequency

A query that takes 5 ms but runs 100,000 times per minute may matter more than a query that takes 2 seconds and runs once per hour.

Evaluate:

```text
query latency
×
execution frequency
×
concurrency
```

Useful PostgreSQL tooling includes `pg_stat_statements`.

The production question is not:

> Is this query fast?

It is:

> Is this workload acceptable for the database capacity and latency requirements?

---

## Filtering Large Tables

For large tables:

- Avoid unrestricted scans when the API does not need them.
- Use selective predicates.
- Use keyset pagination for deep traversal.
- Avoid unnecessary function transformations.
- Validate indexes with execution plans.
- Keep result sets bounded.
- Consider partition pruning for lifecycle-oriented data.
- Monitor query frequency.
- Avoid repeatedly executing expensive filters from application loops.

A filter that is correct at small scale may become a production bottleneck as data grows.

---

## Filtering and Partition Pruning

Suppose orders are partitioned by time.

A query such as:

```sql
SELECT
    id,
    customer_id,
    status
FROM orders
WHERE created_at >= $1
  AND created_at < $2;
```

may allow PostgreSQL to prune partitions that cannot contain matching rows.

This can reduce the amount of data that must be scanned.

Partitioning is not a replacement for good filtering or indexing. It is an additional physical organization strategy.

## Filtering and Caching

Repeated filters may be candidates for Redis caching.

For example:

```text
GET /products?category=electronics&active=true
        ↓
Cache key
        ↓
Redis
        ↓
PostgreSQL on miss
```

Cache keys must include every parameter that affects the result.

Incorrect:

```text
products:active
```

when the response also depends on:

```text
tenant
category
region
price range
```

could return incorrect or cross-tenant data.

Filtering logic and cache-key design must remain consistent.

---

## Filtering and Read Replicas

A filtered read can be routed to a replica:

```text
API
 ↓
Read router
 ↓
Replica
 ↓
Filtered query
```

But replica lag can cause recently created or updated rows to be missing from the result.

For example:

```text
POST /orders
↓
Primary commit

GET /orders?status=completed
↓
Replica
↓
Order not visible yet
```

When filtering is part of a user-visible workflow immediately after a write, consistency requirements should determine the read destination.

## Filtering and Background Jobs

Celery jobs frequently perform filtered database operations:

```sql
SELECT
    id
FROM customers
WHERE status = 'active'
  AND created_at < $1
ORDER BY id
LIMIT 5000;
```

For large datasets:

- Process bounded batches.
- Use stable ordering.
- Track progress durably.
- Avoid unbounded scans.
- Throttle worker concurrency.
- Monitor database CPU, I/O, lock waits, and replica lag.

Do not solve a slow batch job simply by launching more workers. More workers can amplify database contention.

## Filtering Security

Filtering is often an authorization boundary.

Consider:

```sql
SELECT *
FROM invoices
WHERE id = $1;
```

This answers:

> Does invoice `id` exist?

It does not necessarily answer:

> Is this invoice accessible to the requesting user?

A safer resource-scoped query might be:

```sql
SELECT
    id,
    amount,
    status
FROM invoices
WHERE id = $1
  AND organization_id = $2;
```

This is particularly important in:

- Multi-tenant SaaS.
- Admin APIs.
- Microservices.
- Internal dashboards.
- Background jobs.
- Customer-facing REST endpoints.

## Common Filtering Mistakes

### Comparing NULL With `=`

Incorrect:

```sql
WHERE last_login_at = NULL;
```

Correct:

```sql
WHERE last_login_at IS NULL;
```

### Misusing NOT IN

Potentially dangerous:

```sql
WHERE id NOT IN (SELECT id FROM other_table);
```

when the subquery can contain `NULL`.

Prefer `NOT EXISTS` when the business requirement is non-existence.

### Filtering a LEFT JOIN in WHERE

Incorrect for many outer-join requirements:

```sql
LEFT JOIN orders o
    ON o.customer_id = c.id
WHERE o.status = 'completed';
```

Move the child condition into the `ON` clause when unmatched parent rows must remain.

### Ignoring Parentheses

Ambiguous:

```sql
WHERE a = 1 OR b = 2 AND c = 3;
```

Prefer:

```sql
WHERE (a = 1 OR b = 2)
  AND c = 3;
```

when that represents the business rule.

### Applying Functions to Indexed Columns

Potentially problematic:

```sql
WHERE DATE(created_at) = $1;
```

Prefer an explicit timestamp range when appropriate.

### Assuming Every WHERE Clause Uses an Index

PostgreSQL may correctly choose a sequential scan.

Use execution plans to determine whether the chosen access path is appropriate.

### Returning Unlimited Filtered Results

This is dangerous:

```sql
SELECT *
FROM orders
WHERE status = 'completed';
```

for an API endpoint without pagination or another bounded access strategy.

### Building Dynamic SQL From User Input

Never interpolate arbitrary filter values or identifiers into SQL.

Validate filter names separately from filter values and use parameter binding for values.

### Forgetting Tenant Scope

A query that works functionally but omits tenant authorization is a security defect.

## Filtering Troubleshooting Workflow

When a filtered query returns incorrect or slow results:

```text
Define expected result
        ↓
Check predicate semantics
        ↓
Check NULL behavior
        ↓
Check joins/cardinality
        ↓
Check tenant/authorization scope
        ↓
Inspect generated SQL
        ↓
Inspect parameters and data types
        ↓
Run EXPLAIN (ANALYZE, BUFFERS)
        ↓
Check indexes/statistics
        ↓
Check locks / replica lag / pool pressure
        ↓
Validate against production-like data
```

Do not begin by adding an index.

First establish whether the query is:

- Semantically correct.
- Executing the intended SQL.
- Operating against the expected database.
- Reading from the expected consistency point.
- Being affected by concurrency or infrastructure.

## Interview-Oriented Filtering Problems

### Find Customers With No Orders

Requirement:

> Return customers who have never placed an order.

Expected approach:

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);
```

Be prepared to explain why `NOT EXISTS` is preferred over a careless `NOT IN`.

---

### Find Customers With At Least One Large Order

```sql
SELECT
    c.id,
    c.email
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
      AND o.total_amount >= 1000
);
```

The key reasoning is existence rather than join cardinality.

---

### Find Latest Order Per Customer

```sql
SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, id DESC
        ) AS rn
    FROM orders AS o
) AS ranked
WHERE rn = 1;
```

Explain:

- Why the window function is needed.
- Why filtering happens outside the window calculation.
- Why `id` is included as a tie-breaker.

---

### Find Customers With High Lifetime Value

```sql
SELECT
    customer_id,
    SUM(total_amount) AS lifetime_value
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING SUM(total_amount) >= 10000;
```

Explain the difference between:

```sql
WHERE
```

and:

```sql
HAVING
```

and why the order of operations matters.

---

### Multi-Tenant Order Search

Requirement:

> Return completed orders for one organization during a time window.

```sql
SELECT
    id,
    customer_id,
    total_amount,
    created_at
FROM orders
WHERE organization_id = $1
  AND status = 'completed'
  AND created_at >= $2
  AND created_at < $3
ORDER BY created_at DESC, id DESC
LIMIT 100;
```

A senior answer should additionally discuss:

- Tenant authorization.
- Composite index design.
- Pagination.
- Replica consistency.
- RLS if applicable.
- Query-plan validation.
- Large tenant behavior.

- [ ] `NULL` behavior is understood.

- [ ] Tenant/resource authorization is included.
- [ ] Values are parameterized.
- [ ] Dynamic identifiers are allowlisted.
- [ ] Result size is bounded.
- [ ] Pagination strategy is appropriate.
- [ ] Indexes match real access patterns.
- [ ] `EXPLAIN` has been reviewed.
- [ ] Statistics are current enough for the workload.
- [ ] Replica consistency is understood.

- [ ] High-frequency execution is measured.
- [ ] Large-dataset behavior has been tested.
- [ ] Background-job concurrency is bounded.
- [ ] Caching does not bypass authorization.
- [ ] Failure and timeout behavior is understood.

## Senior Filtering Heuristic

When asked to write or review a SQL filter, reason in this order:

```text
What rows should qualify?
        ↓
What is the result grain?
        ↓
What relationships are involved?
        ↓
How does NULL affect the predicate?
        ↓
Is this existence, membership, comparison, or aggregation?
        ↓
What authorization / tenant scope is required?
        ↓
What SQL expresses the intent most directly?
        ↓
What indexes support the access pattern?
        ↓
How large can the result become?
        ↓
How often will the query execute?
        ↓
What happens under concurrency?
        ↓
What happens with replicas, caches, and workers?
        ↓
How will the query be observed in production?
```

This prevents the common mistake of treating SQL filtering as a syntax exercise.

The strongest backend engineers can explain not only **which rows a predicate returns**, but also **why those rows are correct, how PostgreSQL will execute the filter, and what happens when the workload becomes large, concurrent, distributed, or security-sensitive**.

---

## Key Takeaways

- **Filtering is about semantics first:** define the qualifying rows, result grain, `NULL` behavior, join cardinality, and authorization scope before optimizing the predicate.
- **Use the right filtering construct:** `WHERE`, `HAVING`, `EXISTS`, `NOT EXISTS`, window-function filtering, and join predicates express different business requirements.
- **Write index-friendly predicates:** prefer direct comparisons and range conditions, use appropriate composite or partial indexes, and validate decisions with execution plans.
- **Production filtering includes system behavior:** pagination, replicas, connection pools, Redis, Celery, query frequency, large datasets, and tenant isolation all affect correctness and performance.
- **Senior SQL reasoning connects correctness to operations:** a filter must remain safe and predictable under concurrency, scale, retries, failures, and evolving application architecture.
