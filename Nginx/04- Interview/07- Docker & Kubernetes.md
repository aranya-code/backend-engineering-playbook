# Overview

Docker and Kubernetes have become the standard platforms for deploying modern applications, and Nginx plays a central role in both environments. It is commonly used as a reverse proxy, load balancer, API gateway, static file server, and Kubernetes Ingress Controller.

Understanding how Nginx integrates with containerized environments is an important skill for backend developers, DevOps engineers, and cloud architects.

---

# Why Use Nginx in Containers?

Nginx is lightweight, fast, and easy to configure, making it an excellent choice for containerized deployments.

Common reasons include:

- Reverse proxy for backend services
- Serving static assets
- SSL/TLS termination
- Load balancing
- API gateway
- Traffic routing
- Security layer
- HTTP caching

---

# Nginx in Docker

A typical Docker deployment places Nginx in front of one or more application containers.

```text
              Client
                 │
                 ▼
         Nginx Container
                 │
      ┌──────────┴──────────┐
      ▼                     ▼
 Django Container    FastAPI Container
                 │
                 ▼
            PostgreSQL
```

Clients communicate only with the Nginx container.

---

# Docker Networking

Containers communicate over Docker networks.

Example:

```text
Docker Network

├── nginx

├── django

├── fastapi

└── postgres
```

Nginx forwards requests using container names instead of IP addresses.

Example:

```nginx
location / {

    proxy_pass http://django:8000;

}
```

Docker automatically resolves container names within the same network.

# Reverse Proxy for Multiple Services

A single Nginx instance can route requests to multiple containers.

Example:

```nginx
server {

    location /api {

        proxy_pass http://fastapi:8000;

    }

    location /admin {

        proxy_pass http://django:8000;

    }

}
```

Routing is performed based on the request path.

---

# SSL Termination

HTTPS is usually terminated at the Nginx container.

```text
Client

   │

HTTPS

   │

   ▼

Nginx

   │

HTTP

   │

   ▼

Backend Containers
```

Backend containers communicate over the internal Docker network.

---

# Load Balancing Containers

Multiple container instances can be grouped using an upstream block.

Example:

```nginx
upstream backend {

    server app1:8000;

    server app2:8000;

    server app3:8000;

}
```

Requests are distributed across available containers.

# Nginx in Kubernetes

In Kubernetes, Nginx is commonly deployed as an **Ingress Controller**.

Instead of exposing every service individually, incoming traffic is routed through the Ingress Controller.

```text
                Internet
                    │
                    ▼
          Nginx Ingress Controller
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
 User Service   Order Service   Payment Service
```

This provides centralized traffic management.

---

# What is an Ingress?

An Ingress defines routing rules that determine how external traffic reaches Kubernetes services.

Example:

```text
api.example.com/users

        │

        ▼

User Service
```

Different paths or hostnames can be routed to different services.

---

# Typical Kubernetes Flow

```text
Internet

   │

   ▼

Load Balancer

   │

   ▼

Ingress Controller

   │

   ▼

Kubernetes Service

   │

   ▼

Pods
```

Nginx processes incoming requests before forwarding them to Kubernetes services.

# Benefits of Nginx Ingress

Using Nginx as an Ingress Controller provides:

- Centralized routing
- SSL termination
- Load balancing
- URL rewriting
- Rate limiting
- Authentication
- Traffic management

---

# High Availability

In production, multiple Nginx instances are often deployed.

```text
                Load Balancer
                 /         \
                ▼           ▼
          Nginx Pod    Nginx Pod
               │            │
               └──────┬─────┘
                      ▼
              Backend Services
```

If one instance fails, traffic continues through the remaining instances.

An e-commerce platform consists of:

- React frontend
- Django Admin API
- FastAPI Product API
- PostgreSQL database

Architecture:

```text
Users

   │

   ▼

Nginx

   │

   ├────────► React

   │

   ├────────► Django

   │

   └────────► FastAPI

                 │

                 ▼

            PostgreSQL
```

In Kubernetes:

- Nginx Ingress receives all traffic.
- Requests are routed to the appropriate service.
- Each service communicates with its own deployment and database resources.
- SSL is terminated at the Ingress Controller.

---

# Best Practices

- Keep Nginx as the public entry point.
- Use Docker networks instead of hard-coded IP addresses.
- Route requests using service or container names.
- Serve static files directly from Nginx.
- Terminate SSL at Nginx or the Ingress Controller.
- Deploy multiple Nginx instances for high availability.
- Use Kubernetes Ingress for centralized traffic management.
- Monitor Nginx alongside application containers.

---

# Key Takeaways

- Nginx is commonly deployed as a reverse proxy in Docker environments.
- Docker networking allows Nginx to communicate with backend containers using service names.
- In Kubernetes, Nginx is widely used as an Ingress Controller.
- Nginx provides routing, load balancing, SSL termination, and traffic management for containerized applications.
- Combining Nginx with Docker and Kubernetes improves scalability, reliability, and operational consistency in modern production deployments.
